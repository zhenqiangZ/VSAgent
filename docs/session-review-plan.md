# 一次真实会话的复盘：问题清单、事件层重设计、修复顺序

> 对象：2026-10-28 手工跑的一次完整筛选会话（`ses_0001`）。
> 数据源：`~/.vsagent/logs/ses_0001.jsonl`（3.8MB，37 条 `context.metrics`）与
> `~/.vsagent/state.toml`。**本文所有数字都能从这两份文件复算**，复算方法见附录 A。
> 代码位置按 2026-10-28 的 HEAD（`8f621fc`）标注，改动后行号会漂，认函数名。

这份文件回答三个问题，顺序就是它们被提出来的顺序：

1. 这次会话有什么问题（§3，17 条，分 P0–P3）；
2. token 为什么烧得这么快（§2，1.29M 输入换一件事）；
3. **event、子 agent、检索为什么一次都没触发**（§4、§5），以及 event 该改成什么样。

第 3 条是重点：用户给了一个新定义——**task 的每一阶段是一大步，event 把这一大步拆成
一小步一小步地收录，只保留这个流程**。§4 是按这个定义重写的方案，它**取代**
[`event-log-design.md`](event-log-design.md) 里的两条旧约定（见 §9）。

## 二、token 为什么烧得这么快

### 2.1 三个加数

把 37 步的 `context.metrics.usage` 累加，得到每一层被**重复发送**了多少 token：

| 层 | 累计 token | 占比 | 说明 |
| --- | --- | --- | --- |
| RECENT | 679,055 | **52.6%** | 逐条原文，只增不减 |
| 工具定义 | 310,882 | 24.1% | 12,145 × 约 26 步 |
| PREFIX | 208,310 | 16.2% | 5,630 × 37，逐字节不变 |
| TASK | 16,575 | 1.3% | 工作区索引 + 任务状态 |
| HISTORY（摘要） | 10,541 | 0.8% | 只有 `compact` 那一份 |
| MEMORY / EVIDENCE / EVENT | 8,921 | 0.7% | EVENT 全程 0 |

PREFIX 占 16% 不是问题——它逐字节不变，几乎全命中缓存，那是**设计正确**的样子。
问题在 RECENT 与工具定义：两者都是「每一步都把全部历史再发一遍」，而 1M 窗口让
**没有任何机制觉得该停**。

### 2.2 reasoning 是最大单项

模型可见的正文一共 102K 字符，拆开：

| 类别 | 字符 | 占比 |
| --- | --- | --- |
| 中间推理（`reasoning_content`） | 63.5K | **62%** |
| 工具输出 | 24.3K | 24% |
| 正文 / 工具调用参数 | 14.4K | 14% |

推理内容一旦产生就永远留在历史里，**每一步都跟着重发一次**。它比工具输出还大 2.6 倍。

`context.py:1378-1393` 里确实有一条清理规则——把旧的 `reasoning_content` 换成
`REASONING_PLACEHOLDER`——但它**只在 `total > available` 的降级链里触发**。
`available = 1,000,000 × 0.8 - 4,352 = 792,283`，而这一步 `total` 最大只有 5.9K。
**这条规则在这个窗口下是死代码。**

### 2.3 工具定义 12,145 token/步

用同一套装配重建注册表，得到 35 个可见工具、12,145 token，与 trace 最后一步的
`tools=12145` 完全吻合。装族的过程是：

```
3,365（核心 14 个）→ 7,508 → 8,198 → 9,327 → 11,473 → 12,145（8 族）
```

`toolset.py` 的设计意图是「核心常驻 + 领域族现装」，但**装过就不卸**。8 族装完之后，
后面 26 步每一步都在付 12,145 token。按 26 步算，多付的是
`(12,145 - 3,365) × 26 ≈ 228K`，占全部的 17.7%。

### 2.4 缓存被击穿 11 次

正常步与正常步之间命中率 0.93–1.00。这次有 11 次掉到 0.22–0.39：

| 动作 | 次数 | 为什么击穿 |
| --- | --- | --- |
| `load_tools` | 8 | tools 数组变了，整段前缀作废 |
| `task` | 2 | TASK 层在 user 头里，改了它等于改了最后一条消息之前的所有位置 |
| `/compact` | 1 | 消息序列被改写 |

未命中的 456K 里，大约 380K 是这 11 次造成的。**装族本身没错**（一次装完 8 族总共
只付了 8 次），错的是「装族的时机」——模型在第 5、9、12 步反复小批量装，
每次都在最贵的窗口上砍一刀。这条在 §3 P2-2 里给出修法。

### 2.5 结论：三个机制同时失效

| 机制 | 本该做什么 | 实际 |
| --- | --- | --- |
| 摘要（`_summarize`） | 把旧历史压成结论 | `compact_upto=4`，只压了 4 条，之后每步重算「已丢弃 N 条」 |
| 事件（`Event`） | 把一段工作收口成可召回的一行 | **0 条**，三条入口全被条件挡住 |
| 降级链（`degrade`） | 超预算时按顺序丢东西 | 1M 窗口下**永不触发** |

三者失效的共同原因不是 bug，是**阈值按「装不下」设计，而 1M 窗口永远装得下**。
所以修法不能只补条件，得换判据：从「装不下才压」改成「**按阶段压**」——这就是 §4。

### P0-1 · 同一性分母误杀截短构建体

**现象**：模型查 9QTN（α7 ECD，208 aa）对 8V8A 的 394 aa 链，**208 个残基全部对上**，
工具返回 `identity = 0.528`，低于 `IDENTITY_FLOOR = 0.70`，判成「不是同一个蛋白」。
模型据此宣布 `.probe/a7_structures_fetched.md` 里「9QTN 208/208 100%」那行**不可信、
要改正**——把一个正确结论改成了错的。

**根因**：

```python
# vsagent/core/agent/domain/align.py:124
def identity(left: str, right: str) -> float:
    """两条序列的同一性：比对上的相同残基占**较长那条**的比例。"""
    ...
    return matches / max(len(left), len(right))
```

分母取 `max()`。当一条序列是另一条的**截短构建体**（表达构建、ECD、催化域）时，
覆盖度天然低，但同一性可以是 100%。`IDENTITY_FLOOR = 0.70` 的来历（第 40 行注释）
是 EGFR(1M17) vs ABL(1IEP) = 0.356——那一对是**两条都完整**的激酶域，用哪种分母都
远低于 0.70。所以这个阈值从来没有被「截短构建体」这类样本检验过。

同一个数还出现在 5AFN：`0.353` 与旧记录里的「约 69%」其实是**同一个 139 匹配残基**
换了分母。

**修法**：分母改成 `min(len(left), len(right))`（比对长度），并把「覆盖度」作为
**并列输出**而不是判据：

```python
def identity(left, right) -> tuple[float, float]:
    """(同一性, 覆盖度)。同一性 = 匹配 / 较短那条；覆盖度 = 较短 / 较长。"""
```

判据改成「同一性 ≥ 0.70 **且** 覆盖度 ≥ 0.50」，两条都满足才算同一蛋白。
只覆盖 208/394 的构建体应当**通过**（它是同一个蛋白的一段），但结果里必须写明
「只覆盖 208/394 个残基」——那是用户要判断的东西，不是工具替用户判断的。

**为什么不能只调阈值**：把 0.70 降到 0.50 会让真正的近缘同源（同一家族不同亚型，
同一性 55–65%）混进来。口径错了不能靠调参补。

**判据**：新增 `--only identity` 组，含
（a）截短构建体 208/394 全对 → 同一性 1.00、覆盖度 0.53、判 same；
（b）EGFR vs ABL → 判 different；
（c）两条等长序列 → 结果与旧实现逐位相同（不回归）。

**状态：2026-10-28 已实施。** `identity()` 现在返回 `(同一性, 覆盖度)`，判据收在
`same_protein()` 一处；`best_pair()` 按 `(同一性, 覆盖度)` 排序（同一性打平时取覆盖更全的
那条链，否则候选里一小段 100% 相同的肽会挤掉完整同源链）；`Verdict` 多一个 `coverage`
字段，`meta.json` 的 `prior` 逐条带上它。判据组 `--only identity` 13 项，
`--only align-prior` 30 项，全量 3095 项 / smoke 3722 项全绿。
（b）在本机改用「同一性 1.00 但只覆盖 40/274」的真实截短结构：旧口径说「另一个蛋白」，
新口径说「只覆盖 40/274」——1M17 不在这台机器上，那条条件分支仍保留在 `align-prior` 里。

### P0-2 · 项目侧配置整份没生效

**现象**：`dist/.vsagent/tools.toml` **不存在**，而 `dist/.opencode_tui/{tools,permissions,hooks}.toml`
仍在原地。两份 `tools.toml` 都写着 `search_pdb = false` / `search_literature = false` /
`switch_receptor = false`，但这一轮 `load_tools` 把这三个**全都装进来了**；
`permissions.toml` 里的 `deny = ["rm -rf*"]` 也没有加载。

**根因**：改名 `opencode_tui → vsagent` 时，`migrate_legacy_config()`
（`core/paths.py:49`）只处理了**家目录**：

```python
base = home or Path.home()
legacy = base / LEGACY_CONFIG_DIRECTORY      # ~/.opencode_tui
target = base / CONFIG_DIRECTORY             # ~/.vsagent
```

而项目侧那份是另一条路（`permission.py:463`）：

```python
def project_config_directory(root: Path) -> Path:
    if getattr(sys, "frozen", False):
        return Path(sys.executable).parent / CONFIG_DIRECTORY
    return root / CONFIG_DIRECTORY
```

它读 `dist/.vsagent/`，**没有人把 `dist/.opencode_tui/` 搬过去**。家目录迁了、exe 旁边
没迁，于是「用户以为自己关了三个工具」与「模型看到 35 个工具」同时成立。

这条是 P0 而不是 P2：`permissions.toml` 的 deny 规则一起失效，意味着**用户设的安全边界
在打包版上不存在**。

**修法**：`migrate_legacy_config()` 增加第二个参数 `base`（默认 `Path.home()`），
在 `app.py` 装配前对**项目侧目录**再调一次：

```python
migrate_legacy_config(Path.home())
migrate_legacy_config(project_config_directory(self.root).parent)  # dist/ 或仓根
```

顺带在启动日志里打一行「已从 .opencode_tui 迁移到 .vsagent（N 个文件）」，否则这种
静默迁移出问题时没有任何线索。

**判据**：`--only config-migrate`，含
（a）只存在旧目录时迁移成功且内容逐字节相同；
（b）两个目录都存在时不覆盖新的；
（c）打包布局（`sys.frozen`）下项目侧也能迁；
（d）迁移后 `load_tools` 不再报出被关掉的工具。

**状态：2026-10-28 已实施。** `migrate_legacy_config(base=None)` 的 `base` 从
「用户目录」放宽成「任意基目录」，返回值改成 `Migration(source, target, files)`
（`files` 只用来写日志）。`app.py` 现在调两次：一次 `Path.home()`，一次
`project_config_directory(self.root).parent`——**不是 `self.root`**，因为打包后配置目录
跟 `sys.executable` 走，而 `self.root` 是启动目录；从别的目录启动 exe 时两者不是一个地方，
原来那句 `migrate_legacy_config(self.root)` 搬的正是用户没在看的那个目录（这正是
`dist/.opencode_tui` 一直没被搬走的原因）。迁移结果写进 `logs/file-reads.jsonl`，
`purpose = config.migrate`，`detail` 里带「从哪搬到哪、几个文件」。
`configure_file_log()` 提到迁移之前调用，否则这条日志会落到 `cwd/logs` 而不是项目根。
判据组 `--only config-migrate` 11 项，`--only config-paths` 11 项。

### P1-1 · `write_run` 一出生就 stale

**现象**：`artifact#1` 在登记的那一刻 `file_state` 就是 `"stale"`。

**根因**：登记用 **payload 哈希**，对账用**目录指纹**，两个函数不同：

```python
# domain/export.py:1068
fingerprint=fingerprint_text(json.dumps(payload, sort_keys=True))   # bbadd221baba8fb1
```

```python
# ledger.py:750
def _file_state(entry):
    current = fingerprint_path(entry.path)                          # a09305cec4f4f25f
    return "ok" if current == entry.fingerprint else "stale"
```

`fingerprint_path()`（`ledger.py:328`）对目录算的是「清单 + 每个文件内容」；
`fingerprint_text(json.dumps(payload))` 算的是「这一份 JSON 的文本」。两者永不相等。

**影响**：`file_state` 是给模型看的「这个 handle 还作数吗」。一个永远 stale 的产物
等于告诉模型「它可能已经坏了」——这次会话里模型没有据此做错事，但它是一个**恒假的信号**，
迟早会被当真。

**修法**：`export.py:1068` 改成 `fingerprint=fingerprint_path(target)`，写盘之后算。
注意顺序：必须先落盘再算指纹，否则算的是空目录。

**判据**：`--only ledger`，新增「`write_run` 之后立刻 `file_state == "ok"`」与
「改动目录里任一文件后变 stale」。

**状态：2026-10-28 已实施。** `export.py` 的登记改成 `fingerprint=fingerprint_path(target)`，
算在 `_write_json(target / RUN_META, payload)` **之后**——meta.json 落盘之后目录才是最终形态。
判据：`--only ledger` 加两条（按目录算的指纹对账后 ok / 改一个文件后 stale），
`--only write-run` 加三条（一出生 ok / 改 meta.json 后 stale / 改回去又 ok）。

写判据时撞到一个容易踩的点：`Entry.file_state` 是**派生字段**，只有 `reconcile()` 会更新它，
直接读字段永远是登记时的 `ok`。所以判据必须先 `reconcile()` 再读，否则「改了文件还是 ok」
看起来像修复没生效。这也说明 `file_state` 不是一个「登记时就该对」的值——`write_run`
一出生 stale 之所以是 bug，是因为**对账那一步**立刻判它 stale，而不是字段本身错了。

### P1-2 · reasoning 跨轮无条件回传

**现象**：63.5K 字符的推理内容在每一步都重发一次（§2.2），占全部输入约三成。

**根因**：`prompt.py:578` 与 `:590` 两条分支**无条件**写 `item["reasoning_content"]`：

```python
item["reasoning_content"] = marker      # 有 tool_calls 的分支
...
item["reasoning_content"] = marker      # 纯正文的分支
```

DeepSeek 的不变式是「**只要请求带 tools**，每条 assistant 消息都必须回传
`reasoning_content`」，否则 400。这条不变式是硬的，不能违反。但**回传的内容**可以是
占位符——只要字段存在，协议就满足。`REASONING_PLACEHOLDER = "（本步的中间推理已压缩，结论见正文）"`
就是为这个准备的，只是它只在降级链里用（§2.2 说了，那里是死代码）。

**修法**：把「清理」从降级链**提到装配阶段**，按轮次判：

- 当前轮（最后一条 user 消息之后）的 assistant 消息：原文回传。
- 更早轮次的 assistant 消息：`reasoning_content` 换成 `REASONING_PLACEHOLDER`。
- 字段永远存在，协议不变。

**为什么按轮而不是按步**：模型在**同一轮内**需要看到自己上一步的推理来保持连贯
（「我刚才决定用 A 方案，现在验证它」）。跨轮之后任务目标已经写在 TASK 与 FOCUS 里，
旧推理只是冗余。按轮切是最小的、可解释的口径。

**预期**：推理从「37 步全程累积」变成「最多一轮累积」，粗估省 200–250K（15–20%）。

**判据**：`--only reasoning`，含
（a）请求体里每条 assistant 消息都有 `reasoning_content` 字段（协议不变）；
（b）上一轮的推理是占位符、本轮的是原文；
（c）`total` 下降但 `stable_prefix` 逐字节不变。

**状态：2026-10-28 已实施。** `context.placeholder_stale_reasoning()` 在
`split_turns()` 之后、预算估算之前把更早轮次的 `reasoning_content` 换成
`REASONING_PLACEHOLDER`，`ContextBundle.metrics` 多一个 `reasoning_placeholder` 计数。
`EMPTY_REASONING`（本步确实没推理）不换——那一步不是「被压缩了」。
判据组 `--only reasoning` 9 项：三条 assistant 字段齐全、旧推理占位、本轮原文、
`EMPTY_REASONING` 原样、总量 8132 → 4147、system 消息逐字节相同、会话里的 Part 原文未被改动。

### P1-3 · event 三条入口全不可达

**现象**：37 步、7 轮，`events = []`。

**根因**：三个入口各有一个前置条件，这次一个都没满足。

```python
# loop.py:297  /compact
def compact_session(self, session, keep=KEEP_MESSAGES):
    total = len(session.messages)
    if total <= keep:                       # 14 > 6，过
        return total
    target = max(session.compact_upto, total - keep)
    if session.events and target > session.event_end:   # ← 必须先有事件
        record_local_event(session, target, "local")
    session.compact_upto = max(session.compact_upto, target)
```

```python
# loop.py:629 / 631 溢出
if context.dropped:
    if session.events or session.summary_upto > 0:
        ...
    elif await self._summarize(session, message, context.dropped_upto):
```

第三条是模型手动 `record_event`，而 `EVENT_DISCIPLINE`（`prompt.py:350`）写的是
「**一件工作告一段落、准备换下一件时**……触发条件是『话题换了』，不是『做完了』」。
这次会话从头到尾是**同一件事**（4HJO 筛选），话题一次没换，所以模型一次没调。

三条加起来：**`/compact` 要事件先存在，溢出要 `dropped > 0`，手动要话题换**。
1M 窗口下 `dropped` 永远是 0，任务只做一件事所以话题永远不换，于是事件永远不存在，
`/compact` 也就永远不补——**互相等待的死锁**。

**验证**：拿会话的内存副本手动调 `RecordEventTool`，成功产出 `evt_0001`
（覆盖第 5–12 条，产物 7 项，未决 3 项）。工具本身没问题，是**没人调它**。

**修法**：不补条件，改语义。见 §4——event 从「模型判断话题变了才写」改成
「**内核每步自动记，Phase 结束自动封存**」，零请求、零判断。

### P1-4 · `/compact` 的口径按条数，压掉最便宜的

**现象**：在 `total = 42K / 1M`（用了 4%）时按的 `/compact`。`KEEP_MESSAGES = 6`
把 `compact_upto` 从 0 推到 4，压掉最便宜的 4 条（约 3K token）；
最贵的 `msg_0006`（17K 正文 / 359K 累计输入）**原样保留**。同时多一次摘要请求，
并让下一步缓存命中率掉到 0.22。

**根因**：`compact_session` 的判据是**消息条数**（`total - keep`），而成本是
**token**。一条消息的正文可以从 200 字到 17K 字符，条数与成本无关。

**修法**：与 §4 合并解决——Phase 封存按 **token** 判（软预算 120K），
`/compact` 变成「封存当前 Phase」的同义词，不再自己算 `total - keep`。

**判据**：`--only compact`，含「压缩后 RECENT 的 token 下降 ≥ 50%」与
「被压掉的是最旧的那个 Phase，不是最便宜的 4 条」。

### P2-1 · 工具定义 12,145 token/步，装过不卸

**现象**：8 族装完之后，剩下 26 步每步都发 12,145 token 的工具定义。

**根因**：`toolset.py` 只有「装」没有「卸」。族记在 `Session.tool_families` 上，
一旦写进去就再也不会移除。

**修法**（三选一，建议 B）：

- **A. 手动卸族**：加 `unload_tools family=...`。模型要自己管，容易忘，不推荐。
- **B. 按 Phase 自动收敛**：Phase 封存时，把「本 Phase 没用过的族」卸掉。

- **C. 一次性装完**：不改代码，只在提示里要求「一次把要用的族全装上」。

**状态：2026-10-28 已实施（方案 B）。** `toolset.prune_families(session, used,
phase_index)`，挂在 `loop._seal_phase` 上：封存一个阶段时把它**没用过**的族卸掉。

判据：`--only tool-family` 加四条（用过的留着、刚装的不卸、下一个阶段没用过就卸、

### P2-3 · 模型重复读同一份 JSON 4 次

**现象**：`msg_0006` 里同一个 `meta.json` 用 `bash + python3` 读了 4 次，
输出分别是 11.4K / 6.4K / 2.9K / 1.4K 字符。

**根因**：模型第一次自己写了 `[:300]` 截断，只看到前半段，以为「输出被压缩了」，
于是换着法子重读。`MODEL_OUTPUT_LIMIT = 4000`（`prompt.py:17`）在工具返回时
**从中间截断**（`_cut_middle(half=2000)`，`prompt.py:500`），插入语只有一句：

```python
return f"{text[:half]}\n… 省略 {omitted} 字符\n{text[-half:]}"
```

它说了**截掉多少**，没说**原文多长**，更没说**怎么拿全文**。模型看到的是一份
「被省略过」的输出，于是换着法子重读同一个文件——它不知道那 4000 字符已经是
工具能给的全部，也不知道 `read` 带 offset 能翻页。

**修法**：插入语补全三件事——原文多少字符、截掉了中间多少、**怎么拿全文**
（`read` 带 offset，或 `grep` 定位）。例如：

```
… 省略 7842 字符（原文 11842 字符，工具单次上限 4000）
   要全文：read <path> offset=0 limit=2000，或 grep 定位关键行
```

**判据**：`--only output-limit`，含「截断文案里同时有『原文 N 字符』与『read … offset』」。

**状态：2026-10-28 已实施。** `_cut_middle()` 多两个参数：`total`（压缩**之前**的长度）与
`hint`（给模型的下一步）。`truncate_for_model()` 传原文长度 + 「read <path> offset=0
limit=2000 分段读，或 grep 定位关键行；单次最多给 4000 字符——重读同一个文件也一样」。
摘要那条路只传 `total`，不带翻页提示（那里没有人会去 `read` 一个文件）。
判据组 `--only output-limit` 7 项。

### P2-4 · 子 agent 没有任何派发规则

**现象**：0 次 `spawn_agent`。

**根因**：`stable_prefix`（5,630 token / 7,383 字符）**全文不含 `spawn_agent`**。
模型只在工具清单里看到它的一行 description：

```python
"从当前会话 fork 一个子 agent，在后台独立运行，立即返回、不等待结果。"
"适合把一段可以并行推进的调研或计算分出去；同一个任务不要重复派发。"
```

这段只在**模型已经想到要用它**的时候才有用。系统提示里没有任何一句说
「什么时候该派」，推理内容里也从未出现 spawn / 子 agent / 并行 等词。

`SUBAGENT_DISCIPLINE`（`prompt.py:366`）是给**子 agent 自己**看的
（「你是从父会话分出的子 agent」），父会话看不到。

**修法**：在 PREFIX 的工作纪律里加一段**父会话视角**的派发规则，三条就够：

1. **该派**：一件事可以拆成两个以上互不依赖的独立调研（查两个靶点的结构 /
   两个口袋的文献），或者一次要等很久的计算。
2. **不该派**：一件事只需要一两次工具调用；或者子任务依赖当前上下文里的中间结论
   （子 agent 看不到父会话的推理）。
3. **派完不要自己再做一遍**：`spawn_agent` 立即返回，结果是稍后的事件，不是现在。

**为什么不是「多派点」**：子 agent 有自己的上下文与步数，派出去的成本不低。
规则要能同时挡住「该派不派」和「不该派乱派」。

**判据**：`--only env-block` 同组的 `--only prefix`，含「PREFIX 里有 spawn_agent 字样」
与「PREFIX 逐字节稳定（不含日期）」。

**状态：2026-10-28 已实施。** 新增 `SPAWN_DISCIPLINE`，只在 `session.depth == 0` 时
拼进 `stable_prefix()`——子 agent 不能再派，给它看只是每步白付额度。
判据写在 `--only prompt`（组名 `prompt` 已覆盖前缀断言）：前缀含「该派子 agent」与
`spawn_agent`、含「子 agent 看不到你的推理」，而子会话的前缀里**没有**这一段。

## 四、事件层重设计

### 4.1 用户的定义

> 「你可以把 task 的每一阶段理解为一大步，event 就是把这一大步拆解为一小步，
> 把每一小步的过程给收录，只保留这个流程。」

拆开是四层，不是三层：

| 词 | 是什么 | 边界怎么定 | 谁产生 |
| --- | --- | --- | --- |
| **Task** | 用户交办的一件事 | 一条用户消息 | 用户 |
| **Phase** | 一大步（「准备受体」「算口袋」「对接」） | 默认 = 一轮（turn）；可被软预算或显式调用提前切开 | 内核判，模型可命名 |
| **Step** | 一小步（一次模型往返 + 它的工具调用） | 一次 `_run_steps` 迭代 | 内核自动记 |
| **Event** | 一个 Phase 的 Step 流水 | 与 Phase 同边界 | 内核自动封存 |

**关键差别**：旧设计里 Event 是「一段工作的摘要」，模型判断「话题变了」才写；
新设计里 Event 是「一个 Phase 的**过程记录**」，**内核每步都记，Phase 结束自动封存**。
模型不再决定「要不要记」，只决定「这个 Phase 叫什么、结论是什么」。

这样做的直接后果：**它不再依赖任何模型判断**，也就不可能像这次一样一次都不触发。

### 4.2 为什么旧设计一次都没触发

三条入口的死锁（详见 §3 P1-3）本质上是同一个错误：**把「记录」这件事挂在
「压缩」上**。1M 窗口不需要压缩，于是记录也不发生。而记录的价值与窗口大小无关——
用户要的是「回头能看懂这一步一步做了什么」，不是「装不下时丢点东西」。

新设计把两者解耦：**记录每步都做（零成本），压缩只是记录的副产品**。

### 4.3 数据模型

```python
@dataclass
class Step:
    seq: int                 # Phase 内连号，1 起
    intent: str              # 这一步想干什么，≤60 字，本地拼
    tools: list[str]         # 本步调用的工具名，按调用顺序
    args: list[str]          # 每个调用的关键参数，≤80 字/条
    result: str              # 一句话结果：成功/失败 + 首行，≤120 字
    artifacts: list[str]     # 本步新登记的 handle
    issues: list[str]        # 失败项（只记首行）
    message_index: int       # 落在哪条消息上
    part_start: int          # 本步第一个 Part 的下标
    part_end: int            # 本步最后一个 Part 的下标（开区间）
```

```python
@dataclass
class Event:                 # 名字保留，语义变成「一个 Phase」
    id: str                  # evt_0001
    title: str               # Phase 名，≤40 字
    summary: str             # Phase 结论，≤400 字
    phase_index: int         # 第几个 Phase，1 起
    steps: list[Step]        # 流水
    start: int               # 消息下标，闭
    end: int                 # 消息下标，开
    tokens: int              # 这一段原文的估算 token（软预算用）
    kind: str                # manual / auto / local
    degraded: bool           # 标题与结论是本地拼的
```

`actions` / `artifacts` / `issues` 三个旧字段**不再单独存**——它们从 `steps` 里
聚合出来（`Event.artifacts` 变成 property）。理由：存两份必然漂移，而这次会话里
已经出现过「同一件事两个数字对不上」的 P3-3 / P3-4。

**不存 reasoning**。`Step.intent` 是**本地从工具调用拼出来的**（工具名 + 关键参数），
不是模型的自述。理由有三：

1. 模型的自述要花请求，而记录必须零请求；
2. 自述会美化——「验证受体质量」比「读了一下文件」好听，但后者才是过程；
3. reasoning 是 §2.2 里最大的成本项，把它搬进流水等于把问题原样搬过去。

### 4.4 记录时机：三步，全部零请求

**Step（每步，在 `_run_steps` 的工具执行完之后）**

```python
def record_step(session, *, step_no, parts, message_index):
    """把这一步的 Part 折成一条 Step。不调模型、不读 reasoning。"""
```

从 `parts` 里取：`tool_call` 的 name + arguments（截断）、`tool_result` 的
status + 首行、`tool_meta` 里的 handle。这些都是**已经算好的**，纯本地拼装。

**Phase 封存（四个时机，取先到者）**

| 时机 | 触发点 | 说明 |
| --- | --- | --- |
| 轮末 | `turn.done` | 默认边界。一轮 = 一大步，这是最常见的情况 |
| 新用户消息 | `stream_reply` 入口 | 用户打断/追加时，上一轮没走完也要封 |
| 软预算 | 当前 Phase 的原文估算 > 120K token | 一轮跑了 30 步的情况，防止单个 Phase 无限长 |
| 显式 | 模型调 `close_phase(title, summary)` | **只命名，不切分**：名字在封存时取用（§4.14）。轮中途切不开——一条 assistant 消息装着一整轮的所有步，而 `Event.end` 是消息下标 |

**封存做什么**：

1. 若模型没调 `close_phase`，**标题由本地拼**（沿用 `build_local_event` 的三条规则：
   有用户原话取前两句，否则「工具：前 3 个 等 N 个」，再否则「第 a–b 条」）。
   结论也由本地拼：「N 步，M 个工具，产物 K 个，未决 J 项」。
2. 计算 `tokens`（这一段原文的估算）。
3. 追加到 `session.events`，维护连续覆盖不变式。
4. 若「已封存的 Phase 数 > `keep_last_phase_raw`」→ 把**更早的 Phase** 从 RECENT
   的可见范围里移出（只影响装配，不删消息）。

**模型什么时候写标题与结论**：`close_phase` 是**可选**的，而且它**不切分阶段**
（早期设计里它是「提前切」的入口，实测根本切不开，见 §4.14）。它只负责把标题与结论
记在会话上，轮末封存时取用；没给就用本地拼的那份——`degraded=True`。

> 这与旧设计「`record_event` 的 title 与 summary 必填」是同一个思路：
> **收口不花请求**。区别是旧设计要求模型**主动想起**要收口，新设计是
> **内核先兜底，模型想改写再改写**。

### 4.5 渲染

事件块仍然是一条单独的 user 消息，在 TASK 之后、RECENT 之前。格式：

```
【阶段 2】准备受体与口袋（12 步 · 原文 41K token 已归档）
  1. 查 4HJO 有哪些链 → bash ×1 · 失败：目录不存在
  2. 取结构 → fetch_structure(4HJO) · 成功 → structure#1
  3. 看链与配体 → bash ×2 · 成功：5 链，配体 EPJ
  4. 登记受体 → import_structure(structure#1, chain=A) → receptor#1
  ...
  11. 定口袋 → define_pocket(receptor#1, 12 残基) → pocket#1
  12. 开查看器 → open_viewer(artifact#1) · 失败：服务未监听
  结论：受体 receptor#1 就绪；口袋 A 由共晶配体 EPJ 定义，12 个残基。
  未决：查看器未启动。
```

三条渲染规则：

1. **每步一行**，超过 12 步时只留「前 3 + 后 3 + 中间省略 N 步」——中间那些
   用 `recall_event(evt, step)` 取。
2. **失败必须留在流水里**。旧设计把失败塞进 `issues` 一个单独列表，读起来像
   「附加信息」；新设计让失败**长在它发生的那一步上**——「第 1 步失败了，
   所以第 2 步换了个做法」这个因果只有并排才看得出来。
3. **结论与未决是 Phase 级的**，与 Step 分开。它们回答「这一大步的结果是什么」，
   Step 回答「怎么走到的」。

### 4.6 覆盖与召回

**连续覆盖不变式保留**，但更容易成立：Phase 边界天然对齐 turn 边界，
而 turn 边界天然对齐消息边界。

```python
Event.start == 前一条 Event.end
Event[0].start == session.summary_upto
RECENT 从 Event[-1].end 开始
```

`keep_last_phase_raw = 1`：最近一个 Phase 的原文**仍在 RECENT 里**，
所以「刚做完的事」是逐字可查的，不依赖流水。更早的 Phase 只留流水。

**召回**：

```
recall_event()                  # 列所有 Phase：编号 / 标题 / 步数 / 起止
recall_event("evt_0003")        # 读一个 Phase 的完整流水（含被省略的中间步）
recall_event("evt_0003", 7)     # 读第 7 步的原始 Part（工具输出正文）
```

第三条是新增的：**Step 级召回**。旧设计只能召回到「事件」这一层，读到的是摘要；
新设计能一路回到「那一次 `bash` 到底打印了什么」。这是 `part_start/part_end` 存在的理由。

### 4.7 与 summary、/compact 的关系

| 机制 | 新定位 |
| --- | --- |
| **Event（Phase 流水）** | 主力。承担「历史里发生了什么」的全部职责 |
| **summary** | **退休**。它的三段（目标/改动/待办）已经分别由 TASK、Step 流水、Phase 结论覆盖 |
| **/compact** | 变成「封存当前 Phase」的同义词，不再自己算 `total - keep` |
| **降级链** | 保留，但 EVENT 层的优先级提高（见下） |

**summary 退休的理由**：这次会话里 `summary_upto = 4`，摘要只覆盖了最早 4 条消息，
之后 33 步的内容既不在摘要里也不在事件里——它就在 RECENT 里，因为窗口够大。
一旦按 Phase 归档，摘要要覆盖的区间就变成空的。留着它只会让同一段内容被说两遍
（这正是 `event-log-design.md` §5 里「摘要与事件不重叠」那条规则要防的）。

**降级顺序调整**（`context.py` 的 `degrade`）：

```
旧：evidence_detail → history_summary → recent_tool_clear → event_layer → memory → ...
新：evidence_detail → recent_tool_clear → event_step_detail → event_layer → memory → ...
```

`event_step_detail` 是新增的一档：把**已封存 Phase** 的 Step 从「一行一步」
压成「一行一阶段」（只留标题 + 结论）。这比整块丢掉事件温和——标题与结论还在，
丢的是过程。

### 4.8 成本预期

| 项 | 现在 | 改造后 | 依据 |
| --- | --- | --- | --- |
| RECENT | 679K | ~200K | 只留最近 1 个 Phase 原文（`keep_last_phase_raw=1`） |
| reasoning | ~380K（估） | ~130K | 跨轮换占位（P1-2） |
| 工具定义 | 311K | ~180K | Phase 收敛卸族（P2-1） |
| PREFIX | 208K | 208K | 不变（设计正确） |
| EVENT | 0 | ~25K | 10 个 Phase × 约 2.5K，冻结不涨 |
| 其他 | 21K | 21K | — |
| **合计** | **1.29M** | **约 460K** | **降 64%** |

这个估算里最大的不确定项是「一轮有多少步」。这次 7 轮 37 步，平均 5.3 步/轮，
按这个算 Phase 流水很小。如果某一轮跑 30 步，软预算 120K 会把它切成几个 Phase，
总量不变、只是粒度变细。

**实测见 §4.10：同一份会话重放出来是 1.23M → 800K（−35.2%），不是 −64%。**
差在工具定义（这次一个阶段装了 8 个族）与 RECENT 里的工具正文；降幅随会话变长而变大，
37 步只是刚过拐点。

### 4.9 不做什么

| 想法 | 为什么不做 |
| --- | --- |
| 让模型每步写一句 intent | 每步一次请求，37 步就是 37 次；而且模型的自述会美化过程 |
| 把 reasoning 存进 Step | §2.2 说了，那是最大的成本项，搬进流水等于没解决问题 |
| 事件与摘要并存 | 覆盖区间会重叠，同一段内容说两遍 |
| 给 Event 加 `PartType` | 事件只进请求体与 `/events`，不必牵动 TUI / web 两套渲染（沿用旧结论） |
| 每步都写盘 | 落盘在 Phase 封存时做一次；Step 只在内存里累积，崩溃丢失可接受（RECENT 还在） |

**状态：2026-10-28 已实施。** 落地时定下五件方案里没写死的事，都记在这里，
免得下次读代码时以为它们是被误加的：

1. **`seal_phase(force=...)` 分两种覆盖**。轮末遇到「纯聊天的一轮」（一个工具都没调）
   不封——`force=False`，否则事件层会被一堆空阶段占满；溢出 / `/compact` / 强行腾地方
   用 `force=True`，**必须封**，不封就是那一段原文两边都不在。
   这个区分是实测逼出来的：不加它，40 条纯文本消息的长会话溢出时封不出任何东西，
   装配直接报 `ContextAssemblyError`。
2. **`keep_last_phase_raw` 的实现方式**是 `compact = max(compact_upto, events[-1].start)`
   ——最近一个阶段留在 RECENT 里，事件块只铺 `end <= compact` 的那些。
   因此 **`sanitize_events()` 不再把 `compact_upto` 推到事件末端**：那是硬边界，
   推过去会让刚做完的一步立刻失去原文。`compact_upto` 从此只表示
   「手动 / 溢出推出来的位置」。
3. **`/compact` 是硬边界**，与自动封存不同：它把整段封成一个阶段并把 `compact_upto`
   推到末端，连「最近一段留原文」也不留——用户按它就是要腾地方。
   它不再算 `total - keep`（P1-4 的根因），只在会话不足 `KEEP_MESSAGES` 条时直接返回。
4. **`close_phase` 的 `summary` 可选**，`title` 必填。标题缺了退回让模型补（不代写），
   结论缺了本地拼「N 步、产物、未决」——收口仍然不花请求。
5. **摘要真的退休了，但代码留着**。`_summarize` 现在只剩「首轮就溢出、连一段都封不出来」
   这一条兜底；阶段一旦存在，它就立即返回 False。删掉它要连 `summary` 字段、
   `Layer.HISTORY`、`SUMMARY_INSTRUCTION` 一起动，那是另一件事，不在这一轮里做。
6. **旧事件折成「一步」而不是 `steps=[]`**（§6 原计划写的是后者）。`from_dict` 见到
   没有 `steps` 的旧形状，就把 `actions` / `artifacts` / `issues` 折成一条 Step：
   内容一个字不丢，只是粒度与新的流水不同。折成空流水的话，`/events` 与
   `recall_event` 读到的旧历史会变成「有标题没过程」，而数据其实还在。

判据：`--only event-log`（76 项）、`--only event-capture`（22 项）、
`--only compact`（13 项）、`--only phase-compaction`（13 项）。
全量 `test_agent` 3185 项、`test_smoke` 3813 项，均 exit 0。

成本实测见 §4.10。

### 4.10 实测：同一份长会话的重放（2026-10-28）

§4.8 是估算，这里量了一遍。样本是 `~/.vsagent/logs/ses_0001.jsonl` 那次真实会话
——改造前跑出来的，7 轮 37 步 14 条消息，trace 里有 37 条 `context.metrics`。
做法是把同一份消息取回来，用**改造后**的 `ContextAssembler` 逐步重放：
每一步按当时该有的历史装配一次，取 `usage` 各层。脚本 `tools/replay_cost.py`
（`python tools/replay_cost.py --session ses_0001`，不调模型、不联网），
它自己会去找同名的 trace 做对照，`--json` 可以把逐步数据落盘。

三处必须对齐，否则数字没有可比性：

1. **按 `STEP_START` 切步，不按工具调用切**。一步可能没有工具（纯回答），
   也可能一次调三个——按工具切会把 37 步算成 40 多步，和 37 条度量对不上。
2. **补上 `load_tools` 的副作用**。族表决定下一步发多少工具定义；重放里不补，
   工具定义会一直停在核心那一份（3.5K），凭空省下一大截。
3. **去掉旧会话里那 12 条 `COMPACTION` 部件**。它们是「历史超窗 → 摘要」那条路的
   产物，新设计在 1M 窗口下一次都不会产生。留着等于拿旧包袱算新账。

| 项 | 改造前（trace 实测） | 改造后（重放） | 变化 |
| --- | --- | --- | --- |
| PREFIX | 208,310 | 220,705 | +6.0% |
| 记忆 | 6,993 | 6,993 | 0 |

| **合计** | **1,234,284** | **799,762** | **−35.2%** |
| 其中推理 | 331,341 | 61,862 | **−81.3%** |
| 每步均值 | 33,359 | 21,615 | −35.2% |
| 单步峰值 | 50,860 | 31,216 | −38.6% |

（`history` 层没单列：它是 `_compose` 里「header 减去各段」的残差，改造后是负数，
不代表真实用量。摘要本身已经退休，这一段改造后就是 0。）

PREFIX 涨的 6% 就是新加的两段文字：阶段纪律 290 token + 装族引导约 45，

   直到第 24 步（下一轮开始）才卸掉那 4 个族（8,364 → 4,221）。
   族收敛挂在**阶段边界**（P2-1），阶段内不卸。估算假设「典型阶段只用两三个族」，

   都把前面几步重发一遍」，这是无状态接口的固有成本，不是某一层的漏出。

| 6 | 7 | 303,588 | 122,502 | −59.6% |
| 7 | 5 | 246,673 | 93,747 | −62.0% |

前三轮几乎不降：第 1、2 轮各一步，本来就没多少历史；第 3 轮是第一个长阶段，
前面没有可封存的阶段，族也刚装上，事件层还空着。**从第 4 轮起**才既有阶段可归档、
又有族可卸，降幅落在 20%–64%。所以这张表真正说明的是：**会话越长，降幅越大**，
37 步只是刚过拐点。

一句话结论：**这次改造在 37 步的会话上把上下文降了 35%，不是估算的 64%。**
剩下的两个大头是 PREFIX（221K，每步固定 5.9K，占 28%）与工具定义（256K）。
前者是缓存友好但计费不免费的部分，要降只能压 `AGENTS.md`；后者量过「阶段内也收敛」，**结论是不做**（§4.12）。

**重放的三处失真**（方向已知，量级都小）：

- `TASK` 用最终的工作区索引，前几步其实还没有那些产物 → 偏高约 2.7K。
- 证据层没模拟（它是循环层的运行时状态，不是消息里的东西）→ 偏低约 1.9K。
- 事件的标题与结论是本地兜底那份；模型真调 `close_phase` 会稍长 → 偏低一点。

### 4.11 工具输出：上限一直在，问题是压过头

§4.10 初稿把 RECENT 偏大归因于「一次 bash 返回 11.4K 字符」，**这是错的**。
`truncate_for_model` 的 4000 字符上限一直都在（`MODEL_OUTPUT_LIMIT`，旧代码里就有），
那条输出发给模型的只有 **161 字符**。

但顺着查下去发现另一个问题：**压缩把结构化清单整段吃掉了**。

```
原 11,462 字符 → 161 字符
top keys: [...]
n pockets: 20
… 压缩掉 158 行过程输出
   id : P20
   label : 9Z9 位点
```

20 个口袋的中心、半径、来源全没了。会话里模型下一句推理原文是：

> The output got compressed. I need to re-read the pockets info in a controlled way
> — print compactly, maybe only key fields and limit lines.

然后它重跑了一遍命令（多花一整步，约 14K token）换回自己已经拿到手的数据。

**根因**：`compress_tool_output` 中间段只留 `is_key_line()` 认的行——报错与结论。
结构化输出（口袋清单、逐条比对表、逐文件统计）里一行都不匹配，于是整段被压成一句
「省略 N 行」。这不是「限制得不够」，是「限制的方式对这类内容不成立」。

**修法**（`prompt.py`）：中间段改成**按窗口留 3 行**（`COMPRESS_SAMPLE=8`、
`COMPRESS_KEEP=3`），关键行照旧逐字留。窗口宽度试过 1/2/3：

| 每窗口留几行 | 压缩后 | 留住了几个口袋中心 |
| --- | --- | --- |
| 1（单行抽样） | 307 字符 / 88 token | 0（正好和「每 8 行一条记录」对齐，只留下 id） |
| 2 | 1,742 字符 / 446 token | 20 |
| 3 | 2,061 字符 / 526 token | 20（还多带了 radius，`define_pocket` 要用） |

取 3：id + center + radius 正好是下一步要的字段。超过 4000 字符的日志会在深档被压到
只剩关键行，所以这一档放宽不会让进度行回到上下文里。

另外两处小改：省略说明在省略 ≥8 行时带上「原文可用 read_turn 取回」（模型以为数据没了
才会重跑）；「压完是不是真的短了」从按 token 比改成按字符比——说明本身也有长度，
用 token 比时「只省三四行 + 一句说明」会被判成没省。

**代价**：重放合计 781,934 → 799,762（+2.3%），换来省掉那次重跑（约 14K）。
净成本约 +4K，但信息不再丢——模型不会因为看不到数据而重算一遍，也不会在重算时
换一个口径。

判据：`--only selective-compression`（300 项，含新加的「结构化清单不能被整段吃掉」）。

### 4.12 阶段内收敛族：量过，不做

§4.10 说工具定义还剩 256K，很自然会想「阶段内也卸族」。量完之后**结论是不做**，
理由是这个会话里「先装后用」的间隔比任何合理的空闲阈值都长：

| 族 | 装载步 | 使用步 | 间隔 |
| --- | --- | --- | --- |
| pocket | 3 | 13, 19 | **10 步** |
| structure | 3 | 7 | 4 步 |
| export | 3 | 8, 11 | 5 步 |
| listing | 3 | 4, 14, 28 | 25 步（跨了阶段） |
| receptor | 18 | 20–24 | 2 步 |

模型是**先批量装、后逐个用**（第 3 步一次装了 4 个族）。任何「N 步没用过就卸」的规则：

- `N < 10`：pocket 在第 13 步被踩断，多一次 `load_tools`（一步，约 10K），
  而省下的定义只有几百 token × 几步。
- `N ≥ 10`：这次一个族都不会被提前卸掉，省 0。

现有的**阶段边界收敛**已经踩断过一次（重放出来的）：第 24 步封存上一阶段时卸掉
listing，第 28 步又调 `describe_entry`（listing 族）。新代码下这一次会先撞一次
`missing_tool_reason`，模型再补一次 `load_tools`——代价是一步。
这条兜底是设计好的，所以现在这样是对的；但把它做得更勤，只会让这种一步变得更常见。

**要让它成立，得先改「装族的时机」而不是「卸族的时机」**：让模型 JIT 装
（P2-2 的引导已经写了，但还没有真实会话验证「装载→使用」的间隔降到 2–3 步）。
拿到那个分布之后再定 `N=4`，判据是「本阶段装过但连续 4 步没再用 → 卸」+
「卸完 `missing_tool_reason` 仍指路」。在那之前加这条规则，只会把一次便宜的
「多发几百 token」换成一次贵的「多走一步」。

### 4.13 真跑一次：四条判据的实测（2026-10-28）

§4.10 是重放，拿不到 `cached`，也看不出模型会不会用 `close_phase`、会不会派子 agent。
所以另起一个探针 `.probe/live_probe.py`：不经界面，直接装 `AgentHost` + `AgentLoop`
（与 `app.py` 同一套零件），真实模型（`deepseek-flash`，窗口按 1M 配），
`AllowAll` 全放行，4 轮：

| 轮 | 提示词 | 结果 |
| --- | --- | --- |
| 1 | 看 `.probe` 目录里有哪些文件，一句话 | `bash` 一次 |
| 2 | 用 uniprot 族查 P36544 的蛋白名与序列长度 | `load_tools(uniprot)` + `fetch_target` |
| 3 | 把前两轮的结论合成一句话 | 纯聊天，零工具 |
| 4 | 同时查 P36544 与 P08172，「这两件事互不依赖，分头做」 | 一次往返里发了**两个** `fetch_target` |

共 8 步、8 条消息、4 个带工具的步、3 条事件。

| # | 判据 | 要求 | 实测 | 结论 |
| --- | --- | --- | --- | --- |
| 1 | 事件不缺席 | `events >= 带工具的轮数 - 1` = 2 | **3** | 通过 |
| 1b | 步不重不漏 | `sum(steps) + pending == 带工具的步数` = 4 | **3** | **不通过 → 已修** |
| 2 | 单步输入 | ≤ 60K | **10,448** | 通过 |
| 3 | 工具定义 | ≤ 9K | **4,265** | 通过 |
| 4 | 缓存命中 | 连续两步 ≥ 0.90 | 全局 **76.2%**，最低 76.2% | **判据本身要改**（见下） |
| 5 | `close_phase` 被采纳 | 至少一次由模型起标题 | **0 / 3**（全是本地拼的，`degraded=True`） | 未采纳 |
| 6 | 子 agent 派发 | 第 4 轮应派出去 | **0 次** | 未触发 |

**1b 是一条真的 bug，不是判据写错了。** 第 2 轮的两步（先 `load_tools`、再
`fetch_target`）落在**同一条 assistant 消息**里（`STEP_START` 切开），而
`seal_phase` 合并流水时用的键是 `message_index`：

```python
merged = {step.message_index: step for step in _steps_from_messages(...)}
```

同一条消息的两步互相覆盖，只剩后一步。回填那一路（`_steps_from_messages`）
也是「一条消息折成一步」，重启之后流水会按消息数而不是步数缩水。
改法：回填按 `STEP_START` 分段，合并单位改成**消息级**——「一条消息只要当场记过步，
就整条以当场记的为准」。不能用 `(消息, part_start)` 做键：回填按分段起点、
当场记的按第一个工具 Part，两边口径不同，按精确键去重会把同一步记两遍
（第一版改法就是这个后果，重放里 `evt_0005` 出现 4 步）。修完重放：
`evt_0004 = [bash]`、`evt_0005 = [load_tools, fetch_target]`、未封存 1 步
（第 4 轮的两个 `fetch_target` 在同一个 step 里），合计 4 = 带工具的步数。

**判据 4 的写法有问题，不是命中率不达标。** 逐步：

| 步 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| input | 8,076 | 8,830 | 8,886 | 9,575 | 9,995 | 9,441 | 9,566 | 10,448 |
| cached | 0 | 8,192 | 8,064 | 7,296 | 8,320 | 8,448 | 9,344 | 8,320 |
| hit | — | 0.93 | 0.91 | 0.76 | 0.83 | 0.90 | 0.98 | 0.80 |

三个跌破 0.90 的位置各有各的原因：

- 第 1 步必然 0（还没有缓存）。
- 第 4 步是 `load_tools` 那一步——判据原文里已经写了「装族那一步除外」。
- 第 5、8 步**是尾部追加，前缀一个字节都没动**（下面有逐步比对）。命中率低只是因为
  分母里含这一步新写进去的内容：一次工具返回就占 1.5–2K，而整条 prompt 只有 10K。
  按「结构上能复用的份额」算，第 8 步的天花板就是 **0.90**，实测 0.80。

所以这条判据在**短会话**上永远判不准：分母含新内容，天花板跟着工具返回的大小走。
它原本要挡的是「请求体里已有的东西被改写」，那就直接量那件事：

> **相邻两步之间，已有消息的内容不变，只允许尾部追加；封存与装族那一步允许
> header / tools 变化。**

这条可以离线断言（重放两次装配、比对消息列表），不必真跑。逐步比对这次 8 次装配：

```
第 1→2 步：前 3 条完全相同，只追加了 2 条
第 2→3 步：前 5 条完全相同，只追加了 2 条
第 3→4 步：前 7 条完全相同，只追加了 2 条
第 4→5 步：前 9 条完全相同，只追加了 2 条
第 5→6 步：第 1 条不同（封存：引用清单出现了）
第 6→7 步：前 10 条完全相同，只追加了 2 条
第 7→8 步：前 12 条完全相同，只追加了 3 条
```

只有 1 处结构性改写，而且正好落在「封存那一步」这个例外里。
同一把尺子量 §4.10 那份 37 步的长会话：5 处改写，3 处是**轮中途用户插话**
（用户在执行中补一句，复述块跟着最后一条用户消息往前走），2 处是封存后引用清单增长，
其余 32 步全是纯追加。前者是「用户随时可以插话」的固有代价，后者是判据允许的例外。

**`close_phase` 0/3。** 三条事件的标题全是 `_local_title` 拼的（`degraded=True`）。
流水本身没问题（步、工具、结果都在），缺的是「这一步在干什么」的那句话。
模型有 3 次机会（每轮末封存前都可以调），一次都没调——提示词里 `close_phase`
是可选动作，没有触发条件。**要么给它一个明确的触发条件**（「本阶段做完了就调一次」），
**要么接受本地标题**（它其实不差：`_local_title` 会取用户原话/工具名）。
先记着，不急着改。

**子 agent 0 次，但并行工具调用是有的。** 第 4 轮明确写了「这两件事互不依赖，分头做」，
模型的选择是**一次往返里发两个 `fetch_target`**（同一个 step，`_run_tools` 顺序执行），
而不是派子 agent。这说明它理解「并行」，只是默认「并行 = 多工具调用」。
P2-4 加的三条规则（`prompt.py:424`）没有改变这个选择——派子 agent 的成本（多一份
上下文、多一轮汇总）在只有两个查询时明显不划算，模型算对了。这条判据的触发条件
应该改成「**十来个互不依赖的子任务**」或者「每个子任务都要读大量原文」，
两个查询不该期待它派。

### 4.14 `close_phase` 改成「只命名」：三次真跑才走通

§4.13 的结论是「0/3，要么补触发条件、要么接受本地标题」。补触发条件这条路走了三步，
前两步都是错的，记下来是因为**每一步的失败原因都不一样**：

| 版本 | 触发条件怎么写的 | 真跑结果 |
| --- | --- | --- |
| v1（原样） | 「觉得这一大步做完了就调」+「轮末会自动封，不调也行」 | **0 次**。三次机会一次没调——「觉得」不是可执行的判断，而「不调也行」是明说的退路 |
| v2 | 加「换事之前，和新事的第一步工具放在同一步」；「收尾前，3 步以上单独调一次」 | **0 次**（两个时机都没触发） |
| v3 | 内核在尾部加一行「本阶段已 N 步」，提示词改成「看到这行就调」 | **11 次，全部失败**：每次都是「这一段还没有可封存的内容」 |

**v3 暴露的才是真问题：`close_phase` 在轮中途根本切不开。** 一条 assistant 消息
装着**一整轮的所有步**（`STEP_START` 切开的是 Part，不是 Message），而 `Event.end`
是消息下标。`seal_phase` 收到 `event_boundary(session, current_index)`，也就是
「当前这条消息之前」——轮到第 4 步时，这一轮的全部内容都在这一条消息里，
于是 `end <= start`，一次都封不出来。模型照着提示调了 11 次，每次都撞同一堵墙，
还多烧了八步。

**改法：`close_phase` 只命名，不切分。**

- 工具把 `title` / `summary` 写到 `Session.phase_title` / `phase_summary`（只在内存里，
  与 `pending_steps` 同一种处理）；
- `seal_phase` 取用这两个字段（模型给的优先于本地拼的），用完清空；
- 工具返回里明说「封存发生在一轮结束时，这一步之后的调用还记在同一阶段里，
  一次就够，别重复调」——v3 那 11 次里有一半是它以为没生效又调了一遍。

**触发条件只剩一个，而且条件由内核摆到眼前**：本阶段走到第 3 步之后，装配时在
**最后一条消息**加一行「本阶段已 N 步，收尾前调一次 close_phase」。为什么放尾部而不是
TASK 头：它每步都变（3 步 → 4 步），进 header 就等于每步改写第 1 条消息，
整条前缀缓存作废（§4.13 量过）。

**真跑（两轮，各 3 步以上）**：

```
evt_0001 degraded=False 「查 .probe/live 目录 + P36544 蛋白名」 3 步 [bash, load_tools, fetch_target]
evt_0002 degraded=False 「数 state.toml 行数、消息段数与 .probe 下 .py 文件数」 3 步 [bash, bash, bash]
close_phase 调用 2 次，两条阶段都是模型命名的
```

代价与副作用，都量了：

- **每轮多一个往返**（收尾那一步），两轮各 5 步而不是 4 步。这是明说的代价：
  提示词里写了「这一条会多花一个往返，两三步就结束的小事没有这行提示」。
- **PREFIX 涨了约 130 token/步**（阶段纪律改写）。这是纯固定开销，但它换掉了
  「每条阶段标题都是用户原话截断」。
- **缓存没受影响**：命中率 97.0 / 80.0 / 94.6 / 93.7 / 98.5 / 98.7 / 98.4 / 95.9，
  80% 那一步是 `load_tools`（判据允许的例外）。
- **`close_phase` 不进流水**：它是记账不是干活，写进流水只会让新阶段第一行
  变成「close_phase」，而它命名的正是上一个阶段。`step_from_parts` 直接跳过它，
  单独调它也不产生 Step。

**没做的：轮中途切分阶段。** 要做就得把 `Event.start/end` 从消息下标改成
`(消息, Part 位置)`，连带 `_range_tokens` / `render_range` / `phase_start` /
装配里的 `compact` 比较 / `sanitize_events` / TOML 序列化一起改，还要保证
「最近一个阶段留原文」在一条消息被两个阶段切开时仍然成立。那是另一件事，
而它要解决的问题（一轮里做了两件不相关的事）在软预算 120K 之前很少真的发生。
现在这条路的代价只是「标题描述的是整轮，不是半轮」——比切不开却假装能切要好。

## 五、两个没触发的机制：子 agent 与检索

### 5.1 事实（子 agent）

- 0 次 `spawn_agent` 调用。
- `stable_prefix` 全文 7,383 字符，**不含 `spawn_agent`**。
- 推理内容里从未出现 spawn / 子 agent / 并行 / 分出去 等词。

### 5.2 根因（子 agent）

三个原因叠加，缺一不可：

1. **没有派发规则**。PREFIX 里没有一句说「什么时候该派」。模型的默认策略是
   「自己做」，因为那是唯一被明确教过的做法。
2. **工具描述只在被想起时才有用**。`spawn_agent` 的 description 写得不错
   （「适合把一段可以并行推进的调研或计算分出去」），但它躺在 35 个工具的定义里，
   模型不会为了「找找有没有能并行的工具」去读一遍工具清单。
3. **这次任务本身不适合并行**。4HJO 的链路是**串行**的：取结构 → 登记受体 →
   准备配体 → 对接。后一步依赖前一步的 handle。**这次没触发是合理的**。

第 3 点很重要：不能把「0 次」直接判成 bug。真正的问题是**如果遇到适合并行的任务，
它也不会派**——因为没有任何规则告诉它「这种时候该派」。

### 5.3 修法（子 agent）

**PREFIX 加三条派发规则**（与 §3 P2-4 同一条）：

```
子 agent：遇到下面两种情形，用 spawn_agent 分出去，不要自己顺序做：
- 两件以上互不依赖的独立调研（例如同时查两个靶点的结构、两个口袋的文献）；
- 一次要等很久的计算。
不要派的：一两次工具调用就能做完的；依赖当前上下文中间结论的（子 agent 看不到你的推理）。
派出去之后不要自己再做一遍——它是后台跑的，结果是稍后的事件。
```

**与 event 的关系**：子 agent 有自己的 Phase 流水。父会话只看到**一个 Step**：
`spawn_agent(调研 9QTN 的变构口袋)`，结果是「子 agent ses_0002 完成：3 条结论」。
子 agent 的 20 步流水留在它自己的会话里，需要时用 `agent_status` 或
`recall_event` 取。**不合并**——合并会让父会话的上下文被一个不相关的过程撑爆。

### 5.4 检索与网页搜索：工具链是通的，缺的是触发条件

2026-10-28 查 `ses_0001`（α7 那次，5 轮 / 14 条消息）的结论：

| 工具 | 调用次数 | 所在族 | 装过族吗 |
| --- | --- | --- | --- |
| `search_literature`（PubMed） | 0 | `literature` | 否 |
| `search_corpus`（本地语料） | 0 | `corpus` | 否 |
| `search_web`（联网，计费） | 0 | `websearch` | 否 |

会话装过 8 族（listing / structure / pocket / export / receptor / chembl / ligand /
docking），这三族一次都没装。四层原因，从硬到软：

1. **开关**（装配层）：`.vsagent/tools.toml` 里 `search_literature = false`
   （同一份还关了 `search_pdb` / `switch_receptor`）。这不是权限拦截——装配时根本不进
   注册表，模型连名字都看不到。这份文件已 gitignore，是本地调试时关的。
2. **族**（装配层）：`search_corpus` / `search_web` 没被关，但分在 `corpus` /
   `websearch` 族，要先 `load_tools`。模型没装。
3. **规则**（提示层）：`AGENTS.md` 第 4 条与 1.1 明确写「不要因为介绍要准确就去检索
   ……否则每次介绍都会变成一次检索远征」。第 3 条消息的 reasoning 原文就是模型**想到
   了并主动放弃**：`Should I do literature search? … The spirit of the rules: don't turn
   every introduction into a retrieval expedition.`
4. **数据**（语料层）：本地库里没有 α7。实测
   `search_corpus("alpha 7 nicotinic acetylcholine receptor")` 返回 33 组，全是
   Nav1.7 / CB1 的示例文献（库是 2 篇 doc + 76 个 web 源）。

**这不是 bug，是现有规则的结果**：第 1 关（把蛋白讲清楚）被明确划给先验知识，检索只
服务「要出处」的场景（规则 4）。α7 这种「先介绍」的对话里，0 次调用符合规则。

**但它暴露了一个真缺口**：规则 4 说「每个数字都要有出处」，而工具链上唯一能给出处的
两条路（`search_corpus` 免费、`search_web` 计费）**在规则里一次都没被提到**。
「先查本地、不够再联网」那句话只写在工具描述里，而工具没装的时候模型读不到。

三条待办，**按顺序修才有意义**（2026-10-28 当天全部落地，见下）：

1. **开开关**：`search_literature` / `search_pdb` / `switch_receptor` 是否恢复，取决于
   要不要 PubMed 与 RCSB 文本检索。不开，规则写了也调不到。
2. **补取证顺序**：若要「介绍 / 取证」先走本地语料，得在 `AGENTS.md` 第 1 关加一条
   ——`search_corpus` → 无相关才用先验知识并标注 → 要最新进展才 `search_web`。只写
   「多检索」会与 1.1 直接打架，模型会退回「自己做」。
3. **补语料**：本地先有 α7 相关文献。不补，第 2 条修好也只是把「没查」换成
   「查了但没有」。

**落地状态（2026-10-28）**：

- 第 1 条：`search_literature` 已从 `.vsagent/tools.toml` 移除（不再禁用），
  装配验证进注册表；`search_pdb` / `switch_receptor` 仍关着（这次用不到）。
- 第 2 条：**已写进 `AGENTS.md` §1.3「取证顺序」**。规则是三步：
  `search_corpus`（免费）→ 命中就用引用号、`read_source` 读原文；本地没有或不相关
  → 要已发表文献用 `search_literature`（PubMed，免费）、要最新进展用 `search_web`
  （计费，前 10 次不问）；都查不到就说「本地语料与 PubMed 都没有查到」。
  三条边界：命中就停、一次取证最多两三轮、只报靶点名那一轮走第 0 关（见下）。
- 第 3 条：验证 `search_web` 时搜了 α7 PAM 相关 10 条网页，已入库入索引
  （`vector_coverage=1.0`），本地对 α7 不再是空库。

**2026-10-30 改**：第 0 关从「不动手、标未核验」改成「先查再讲」——只报靶点名时先
`search_corpus`，本地没有就 `search_web`，搜到的网页进本地语料再检索一遍，介绍里每个
数字带引用号。原先那条「这一轮不调任何工具」与「开头写未核验」一并撤掉。

**判据**：`--only prompt` 新增四条，钉住「规则里有 `search_corpus`」「命中就停」
「PubMed 与联网搜索都点到名字」「查不到要说没查到」。

**这次改动顺带修了两条被前缀撑破的判据**（它们量的是别的东西，不是被测的契约）：

- `COMPACT_WINDOW` 16K → 18K：前缀涨约 700 token 后，16K 时事件块正好被挤出

## 七、验收判据

改造是否成功，看六条。前四条是硬的，后两条是趋势。

1. **事件不再缺席**：一次 5 轮以上的会话结束时
   `len(session.events) >= 带工具的轮数 - 1`，且
   `sum(len(e.steps) for e in events) + 当前 Phase 的步数 == 带工具的步数`。
   **每个 Step 恰好被一个 Phase 收走一次**，不多不少。

   两个「带工具」都不能省：纯聊天的一轮（零工具）按设计 `force=False` 跳过——
   收进去只会得到一堆空阶段；而一轮里的纯回答步也**不产生 Step**
   （`step_from_parts` 见不到工具就返回 None）。这次 7 轮里 2 轮纯聊天，
   出 4 条事件，正好是 `5 - 1`（最后一轮结束时还没封，它在下一次发问时才封）。
   按「轮数 - 1」写这条，会把正常行为判成失败。

   第二句（步不重不漏）在 §4.13 那次真跑里**抓到了一条真 bug**：
   同一条 assistant 消息里的两步被按 `message_index` 合并成一步。
   修法见 §4.13；`test_agent.py --only event` 里补了两条断言钉住它
   （回填按 `STEP_START` 分段、当场记的那份与回填不重复也不丢）。

2. **单步输入有上限**：1M 窗口下，任何一步的 `input` 不超过 **60K**。
   这次是 55.7K 到顶，所以 60K 是个宽松但有效的线——它挡住的是「无上限增长」，
   不是「偶尔到 50K」。

3. **工具定义有上限**：任何一步的 `tools` 不超过 **9K**。
   改造前是 12,145（8 族常驻、装过不卸）；这次重放峰值 **8,364**
   （核心 3.5K + 5 族同时装着：listing / structure / pocket / export / receptor），
   真跑那次峰值 **4,265**（只装了 uniprot 一族）。

   原来写 7K（「核心 + 3 族」），是按「典型阶段用 2–3 族」估的。这份样本第 3 轮的
   第 1 步一次装了 4 个族，7K 当场就破——**判据要比最坏情况宽一档**，否则它挡的是
   正常行为，不是回归。它要挡的东西没变：改造前那条线是 12K，而且只涨不落。

4. **前缀不被改写**：相邻两步之间，**已有消息的内容不变，只允许尾部追加**；
   封存与装族那一步允许 header / tools 变化。

   原来写的是「缓存命中率 ≥ 0.90」，真跑一次发现**这条判据量不出想量的东西**
   （§4.13）：分母里含这一步新追加的内容，10K 的 prompt 里一次工具返回就占 15%，
   天花板本来就在 0.85–0.90 之间。改造前的 0.646 是真的，但那是长会话（60K+）的数，
   拿它当短会话的线只会误伤。

   结构判据可以离线断言：重放相邻两次装配，比对消息列表——真跑那次 8 步里
   只有 1 处改写，正好落在「封存那一步」的例外里。

5. **召回可达**：`recall_event(evt, step)` 能取回任意已封存 Step 的**原始工具输出**，
   且取回的内容与 trace 里那一步的 `part` 逐字节相同。

6. **收口与派发**（趋势，不卡）：3 步以上的轮里，阶段标题由模型命名（真跑 2/2，
   §4.14）；子 agent 在「十来个互不依赖的子任务」那种规模下派得出去（真跑 0 次，
   但那一轮只有两个查询，模型选了「一次往返发两个工具调用」——这个选择是对的，
   是判据的规模定错了）。

**回归**：现有 40 组判据一条都不能红。特别是
`test_agent.py --only context` 里那几条关于「RECENT 整 Turn 搬移、tool_call 与结果不拆散」
的断言——Phase 归档必须建立在它们之上，不是绕过它们。

## 八、风险

| 风险 | 后果 | 缓解 |
| --- | --- | --- |
| Phase 边界切错（一轮里干了两件不相关的事） | 流水混在一起，标题说不清 | 软预算 120K 兜底；标题取首条用户原话，不会全错。`close_phase` **切不开**轮中途（§4.14），它只命名——所以这条风险的兜底是「标题描述整轮」，不是「切成两段」 |
| Step 的 `intent` 本地拼得太粗（「调用了 bash」） | 流水读起来没信息 | `intent` 优先用工具名 + 第一个参数值（`fetch_structure(4HJO)`），比纯工具名有信息；实在拼不出就写工具名，不编 |
| 旧 `state.toml` 迁移出错 | 旧会话打不开 | `from_dict` 里 try/except + `degraded=True` 兜底；迁移前先备份一份 `state.toml.bak` |
| reasoning 跨轮占位让模型丢失上下文 | 长任务连贯性下降 | 只在**跨轮**时占位，同轮内保留；`REASONING_PLACEHOLDER` 明确说「结论见正文」，正文还在 |
| 卸族卸掉了下一步要用的 | 模型找不到工具，转去 bash 自己实现 | 只卸「本 Phase 没用过」的族，且 `load_tools` 能立刻装回来；`missing_tool_reason` 已经会认族并给出装族指令 |
| Phase 流水本身膨胀（100 个 Phase） | EVENT 层吃掉额度 | 事件块额度是 `min(6000, available // 6)`（一个阶段一块之后从 1800 调上来的）；超了先 `event_step_detail` 压成一阶段一行，再裁最旧的并补一行「更早还有 N 个阶段」 |

## 附录 A · 复算方法

```bash
# 每步的 token、分层用量、缓存命中率
.venv/bin/python - <<'EOF'
import json, collections
p = "/home/ubuntu/.vsagent/logs/ses_0001.jsonl"
ms = [json.loads(l)["payload"] for l in open(p)
      if '"context.metrics"' in l]
print("步数", len(ms))
print("input", sum(m["input"] for m in ms))
print("output", sum(m["output"] for m in ms))
print("cached", sum(m["cached"] for m in ms))
agg = collections.Counter()
for m in ms:
    agg["tools"] += m["tools"]
    for k, v in m["usage"].items():
        agg[k] += v
print(dict(agg))
print("最大单步", max(m["input"] for m in ms))
print("tools 取值", sorted({m["tools"] for m in ms}))
EOF

# 事件与压缩状态
grep -n "compact_upto\|summary_upto\|events =" ~/.vsagent/state.toml

# 事件数为 0 的证据
grep -c '"events": 0' ~/.vsagent/logs/ses_0001.jsonl
```

**为什么用 `context.metrics` 而不是 provider 的 usage**：前者是装配器算的
（每层多少 token），后者是服务端报的（一共多少）。两者对得上（`total + tools`
与 `input` 一致），但只有前者能拆开看每一层。
