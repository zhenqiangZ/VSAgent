# 真实会话里看到的失败模式

2026-10-25 两次真实会话（deepseek-flash / 1M 窗口），同一组三问：

1. 「查一下人 EGFR（P00533）在 PDB 里有哪些结构，挑一个带小分子抑制剂的给我编号」
2. 「把 4HJO 的结构取下来并登记成受体」
3. 「把 4HJO 写成一个运行目录，告诉我里面有哪些文件」

两次都跑完了，也都做成了；但同一组问题输入 **442K 与 135K**，差 3.3 倍。
差的那 3 倍几乎全在第 1 轮的步数上（24 步对 7 步）。这份文件只记账，不改代码：
每条写清现象、证据、根因在哪、代价多少，以及**是不是当初刻意的**——刻意的那些
要改就得连理由一起改。

| # | 现象 | 代价 | 根因位置 | 刻意？ |
| --- | --- | --- | --- | --- |
| F1 | 瞬时失败被判成永久失败，模型转去 bash 自建客户端 | ~20 步 / 300K 输入 | `domain/rsearch.py:253`、`:320`，`domain/complexes.py:241`、`:332` | 是（`SearchError` 的 docstring 写着「不重试到底」） |
| F2 | 模型在 Linux 上写 Windows 命令 | 2 步 | `bash` 工具的回执 | 否 |
| F3 | 猜错 handle 编号，`open_viewer` 失败 | 1 步 | 上下文里没有「当前有哪些 handle」的索引 | 否 |
| F4 | 模型不知道状态目录在哪，先试 `./.opencode_tui` | 2 步 | 上下文里没有工作目录 / 状态目录 | 否 |

## F1 · 一次网络抖动把工具判死，模型绕道 20 步

**现象**：第 1 次会话第 1 轮，模型先 `search_pdb({"query": "P00533"})`，失败；
随后它没有重试、也没有改用 `uniprot` 参数，而是 `bash` + `urllib` 自己写脚本
拉 RCSB，连写三个 `.probe/*.py`，中间还试过 `ls .venv/Scripts/`、`which py`。
第 1 轮因此用满 `MAX_STEPS=24`。

**证据**：同一条命令事后手动重跑是成功的——`search_pdb(query="P00533")` 返回
391 条命中、列出 25 条。所以那次失败是瞬时的，不是参数错。

**根因**：`rsearch.search_entries` 用 `except Exception` 把
`http.RetryableToolError` 也归成了 `SearchError`（「这次没搜成」）。循环层看到的是
一个**普通失败**，重试机制根本没启动；模型看到的是「这个工具坏了」，于是自己造一个。
同一份写法一共四处：`rsearch.py:253`（检索）、`rsearch.py:320`（批量取配体）、
`complexes.py:241`（取复合物）、`complexes.py:332`（下载 PDB）。

**为什么当初这么写**：`SearchError` 的 docstring 明确说「当『这次没搜成』，
不重试到底」——那时候更担心的是「网络不通时把步数耗在重试上」。但真实数据说明
代价不对称：重试最多多花 2 次请求，判死要多花 20 步。

**建议**：`except RetryableToolError: raise` 放在 `except Exception` 前面，让循环层
按自己的节奏重试；真的重试完还不行，那时再回「这次没搜成」。四处一起改，
并给「瞬时失败仍然可重试」补一条判据（假 http 抛 `RetryableToolError`，
断言它穿出 `search_entries` 而不是变成 `SearchError`）。

## F2 · Linux 上写 Windows 命令

**现象**：第 2 次会话第 3 轮，模型执行 `bash("cd runs/4hjo && dir /s /b ...")`，
失败，改用 `ls -la` 才拿到文件清单。

**代价**：2 步。不致命，但它是「模型不知道自己在什么平台上」的直接证据。

**建议**：与 Phase 4 的 ENV 块合并解决——把平台写进上下文，比在 `bash` 的失败回执里
猜要稳。若 ENV 块一时不做，退而求其次：`bash` 失败且命令里出现 `dir`/`del`/`type`
时，回执补一句「当前平台是 linux」。

## F3 · 猜错 handle 编号

**现象**：第 1 次会话末尾 `open_viewer({"run": "artifact#2"})` 失败——当时登记表里
只有 `artifact#1`。模型是照前几步见过的编号推的，隔了几步就记串了。

**根因**：handle 只在**工具返回的那一刻**出现在上下文里，之后要么进了证据层、
要么随旧工具结果被清掉。模型要用的时候手里没有索引，只能凭记忆。

**建议**：Phase 4 的「产物索引」正好治这个——`SessionLedger.digest()` 给当前受体
+ 最近 5 个产物，≤10 行。这条不是锦上添花，是**上面这次失败的复现条件**。

## F4 · 不知道状态目录在哪

**现象**：第 1 次会话第 1 轮，模型执行
`bash("cd .opencode_tui/targets && python -c ...")`，失败（相对路径没有这个目录），
随后 `ls ~/.opencode_tui` 才找到。

**根因**：这次实验的状态目录在 `/tmp/vsa-lazy-session`，模型默认它在
`./.opencode_tui`。它没有「状态目录 / 工作目录是哪个」的任何信息，只能猜。

**建议**：并入 ENV 块（工作目录 + 状态目录 + 平台 + 日期）。注意必须放在
**易变区**：日期进了 `PREFIX` 就每天击穿一次缓存，还会红掉
「PREFIX 连续两步字节相等」那条判据。

## 不需要改的（正面证据）

- **按需加载不用教**：两次都自己 `load_tools`，按 structure → uniprot → rsearch →
  export（→ listing）装 4–5 族，没有一次需要提示。每步工具定义 3.1K → 6.0K，
  全量是 12.3K。装族那一步命中率 98.9% → 36.6%，下一步回到 95.9%——一次性。
- **说清下一步的失败文案是有效的**：第 2 次会话模型叫了 `search_pdb({})` 空参数，
  工具回「至少要给一个条件：uniprot / ligand / method / query」，它当场换路，没绕。
  这条正好是 F1 的对照组：**同一份失败预算，写清下一步省 20 步**。
- **零命中不再被当成失败**（`EmptyResult` 那次修正）在这两次里没再触发误判。

## 按代价排序的修法

| 顺序 | 修什么 | 依据 | 风险 |
| --- | --- | --- | --- |
| 1 | F1 重试穿透 | 20 步 vs 2 次请求 | 要改一条刻意写下的设计（`SearchError` 不重试），得连 docstring 一起改 |
| 2 | F3 产物索引 | 猜错 handle 是可复现的 | 无；纯增一层渲染 |
| 3 | F2 + F4 ENV 块 | 各 2 步，但是「模型对环境一无所知」的同一件事 | 位置放错会击穿缓存 |
