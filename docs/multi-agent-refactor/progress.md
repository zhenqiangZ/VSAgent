## 二、问题台账

每条写：现象、根因、解决办法、判据。**没有判据的修复不算完成。**

### P-01 计划要求独立测试文件，仓库只有一个测试入口

- **现象**：Phase 1 要求新增 `tests/test_agent_contracts.py`，而本仓库全部判据在
  `tests/test_agent.py` 的检查组里，用 `--only` 选组。
- **根因**：测试文件是转换器生成的产物，另起一个文件要再配一套入口与夹具。
- **解决**：按仓库惯例加检查组 `contracts`，不新建文件。判据内容按计划写全。
- **判据**：`python tests/test_agent.py --only contracts` 通过。

### P-02 协议层不能依赖运行期模块，但校验要用到枚举

- **现象**：五个协议都要校验状态与类型，容易顺手 import `models.py` 或 `domain/`。
- **根因**：协议的枚举与运行期模型不是同一层，互相引用会形成环。
- **解决**：枚举定义在 `contracts/` 内；校验工具写在 `contracts/base.py`；
  新增一条判据扫描该包源码，出现 `vsagent.app`、`agent.loop`、`agent.domain` 即失败。
- **判据**：`contracts` 组里的"协议层不依赖运行期模块"。

### P-03 验收条件必须能机器检查，否则无法做交付校验

- **现象**：计划写"每个必需交付物至少一条验收条件"，但没规定条件长什么样。
  纯文字条件（"口袋画像科学合理"）在 Phase 8 无法判定。
- **根因**：协议只约束了字段名，没有约束取值。
- **解决**：`acceptance_criteria` 的每一项必须带 `kind`，取值限定为五种：
  `artifact_exists`、`handle_registered`、`evidence_ref`、`approval_recorded`、
  `review_required`。前四种是机器可查的，最后一种是人工或评审 Agent。
- **判据**：`contracts` 组里的"验收条件只接受五种 kind"。

### P-04 子 agent 改共享状态（来自真实任务）

- **现象**：worker 档的子 agent 在"登记一个结构"的任务里准备了受体、切换了当前受体，
  父会话的三项产物被搁置。
- **根因**：工具档位只裁常驻工具，`load_tools` 装进来的领域工具不受档位限制。
- **解决**：`permission.WORKER_DENY` 拦 `switch_receptor`、`prepare_receptor`、
  `prepare_ligands`，循环层按会话深度传入 `worker=True`。
- **判据**：`worker-guard` 组。
- **遗留**：`write_run` 仍可用，多个子 agent 可能撞同一个 `run_id`。

### P-05 同一份任务书，两轮行为不同

- **现象**：同一句"登记 1IEP、报链数"的任务书，第一轮 11 次调用、越界写运行目录，
  第三轮 4 次调用、只做要求的两件事。
- **根因**：行为由自由文本与模型采样共同决定，没有运行期约束。
- **解决**：不改任务书，改为加运行期边界（见 P-04）；这条同时作为
  "不能用任务书替代运行时约束"的证据记在设计稿 §8.1。
- **判据**：无法用单轮判据固定；以 `worker-guard` 的机械判据为准。

### P-06 拆 `scoring` 族时，旧会话会静默丢工具

- **现象**：旧会话的 `tool_families` 里存着 `scoring`；按未知族名忽略会让
  `dock`、`fit_affinity`、`score_affinity` 从清单里消失，模型会以为工具没了。
- **根因**：族名是持久化在会话上的，改名就是一次数据迁移。
- **解决**：`toolset.LEGACY_FAMILIES` 把 `scoring` 展开成 `docking` 与 `affinity`，
  `hidden_names`、`load_tools`、`next_tools` 三处都先展开。
- **判据**：`family-split` 组。

### P-07 "要澄清"与"澄清问题"的关系计划里没定义

- **现象**：`IntentSpec` 同时有 `clarification_required` 与 `needs_clarification`
  两个说法，计划没说两者谁蕴含谁。
- **根因**：一个字段描述状态，另一个描述内容，接口说明里没有把它们绑起来。
- **解决**：定为**单向蕴含**——标了 `needs_clarification` 就必须写出要问什么；
  反过来允许：一个解析成功的任务可以带一句补充提问，不必降级成"没解析出来"。
- **判据**：`contracts` 组的"标了要澄清却没写问题"被拒。

### P-08 交付物与验收条件之间没有连接字段

- **现象**：`required_outputs` 里是 `{name}`，`acceptance_criteria` 里是 `{kind,target}`，
  计划没规定两者怎么对上，"每个交付物至少一条验收条件"就无法机械检查。
- **根因**：协议只写了字段名，没写关联方式。
- **解决**：验收条件用可选的 `output` 指向交付物名，`target` 是被检查的对象
  （产物名、handle、证据编号）；`TaskSpec.uncovered_outputs()` 返回没有条件覆盖的
  交付物，空列表才算通过。
- **判据**：`contracts` 组的"每个交付物都有验收条件"。

### P-09 `AgentTask` 计划里没有状态字段

- **现象**：Phase 10 要求"同一 task_id 只成功派发一次"，幂等判定需要知道这份任务
  处在什么状态；计划的 `AgentTask` 只有输入字段。
- **根因**：协议表按"派发时填什么"设计，没有按"调度器要知道什么"设计。
- **解决**：加 `status`（六种），默认 `pending`；不影响计划的其它字段。
- **判据**：`contracts` 组的往返一致与枚举校验。

### P-10 发现类任务被追问编号（真实模型）

- **现象**："获取 EGFR 的所有候选结合口袋，分析口袋特征和适配分子"被解析成
  三条追问，其中一条要用户先给 PDB 编号和物种。方案 §Phase 2 明确写了这种追问
  是错的：缺编号不是阻塞，任务本身就是去发现。
- **根因**：提示词只说了"不要猜编号"，没说"缺编号不算阻塞"。模型把
  `missing_information` 与 `clarification_required` 混成了一件事。
- **解决**：提示词里把两者分开——前者是信息状态，后者是"不回答就无法开始"；
  并给了正反两类例子（发现类不要问编号；只给名词、说了"这批分子"没给分子才问）。
  第一次修改后追问从 3 条降到 0 条。
- **判据**：`tools/eval_intent_parser.py` 第 2、3 条，要求"不追问"。

### P-11 多目标要不要单列 `multi_objective`

- **现象**："研究 EGFR 并寻找新型抑制剂"被拆成四个具体类型，没有 `multi_objective`。
  两种表示都能用，但下游路由需要知道"这是一件复合的事"，只拆具体类型看不出来。
- **根因**：提示词允许"可多选"，但没有规定复合任务必须带这个标记。
- **解决**：定为**两者都要**——具体类型照常标，同时加 `multi_objective`；
  子目标分解留给 Phase 4。
- **判据**：`tools/eval_intent_parser.py` 第 9 条。

### P-12 加了字段要不要升协议版本

- **现象**：Phase 3 给 `IntentSpec` 加 `turn_mode`，包说明写着"改形状要升版本"，
  但没有任何数据在野外，升版本看起来是多余动作。
- **根因**：版本号同时承担两件事——拒绝更新版本的数据、标记形状变化；后者容易被忽略。
- **解决**：升到 2。旧数据（没有该字段）按 `new_task` 读，仍然能加载；
  版本号只用来拒绝"比程序更新"的数据。这样将来回滚到旧版本时不会把新数据读坏。
- **判据**：`contracts` 组里"协议版本更新"仍然被拒；`IntentSpec` 往返带 `turn_mode`。

### P-13 "继续"里新加的禁止项会丢

- **现象**：用户先说"取全部结构"，再说"继续，但不要用冷冻电镜的"。
  按轮次类型，第二句是 `continue_task`；如果继续任务就不处理它的
  `exclusions`，这句禁止会被静默丢掉。
- **根因**：把"轮次类型"和"要不要合并新要求"当成了同一件事。
- **解决**：合并与轮次类型分开——除 `new_task` / `general_chat` 外，一律把这一句
  新提的约束与禁止项并进任务；只有 `modify_task` 额外替换目标。
  合并只增不减，`revision` 真的变了才加一。
- **判据**：`task-context` 组的"追问里新加的禁止项并进去、旧的没丢"。

### P-14 "改目标"与"加约束"的分界写错了

- **现象**："再多取几个结构，但不要用冷冻电镜的"被判成 `modify_task`。
  这会在这个模型里替换任务目标，把"取全部结构"改成"再多取几个结构"。
- **根因**：提示词把 `modify_task` 定义成"改目标**或**加减约束"，两条不同的
  动作合成了一条；而代码里只有 modify 会替换 objective。
- **解决**：分界线改成唯一一条——**完成的目标本身变没变**。目标不变、只补要求或
  加禁止，一律 `continue_task`（合并规则照旧生效）；换对象、换突变体、换范围才是
  `modify_task`。
- **判据**：`tools/eval_intent_parser.py` 第 13 条。

### P-15 "没给摘要时一律 new_task"把闲聊也吞了

- **现象**："什么是变构调节"没有上下文时被判成 `new_task`，实际是概念问答。
- **根因**：为了不让模型凭空判断"在继续"，提示词写了"没给摘要时一律 new_task"；
  这条同时把 `general_chat` 也压掉了，而闲聊本来就与有没有任务无关。
- **解决**：改成"没给摘要时不可能是在继续、改目标、问结果或恢复，只能在
  new_task 与 general_chat 之间选"。既堵住凭空续接，又留住闲聊。
- **判据**：`tools/eval_intent_parser.py` 第 11 条。

### P-16 计划里的 `task_spec.py` 与协议层重复

- **现象**：Phase 1 已经把 `TaskSpec` 定义在 `contracts/task.py`，Phase 4 的文件表
  又列了一个 `task_spec.py`。
- **根因**：阶段文件表按"每个阶段交付一个模块"写，没有和前一阶段的协议位置对齐。
- **解决**：不新建 `task_spec.py`。数据定义只有一处（`contracts/task.py`），
  Phase 4 只加编译器 `task_compiler.py`。
- **判据**：`contracts` 与 `task-compiler` 两组共用同一个 `TaskSpec`。

### P-17 排除项对编译的影响没有规定

- **现象**：用户说"不要对接"，计划里仍可能出现筛选那一段——排除项只是文本，
  不参与编译。
- **根因**：计划只写了"`exclusions` 原样继承"，没说它要不要影响编译结果。
- **解决**：两条一起做——原样继承；并且删掉与它冲突的模板（不要对接／筛选 →
  去掉 `virtual_screening`）。删掉的模板记一条警告，写清去掉了哪些意图。
- **判据**：`task-compiler` 组的"说了不要对接，筛选那一段就不在计划里"。

### P-18 没有模板的意图怎么处理

- **现象**：十四种意图里 `multi_objective` 是标记；将来还可能加新类型。没有任何
  专用模板时，编译器不能什么都不产出。
- **根因**：计划的编译规则默认"每种意图都有模板"。
- **解决**：退回一份最小通用模板（交付一份 `TaskReport`，两条验收条件），并记
  `uncovered_intent` 警告。**不静默降级**：警告会进 trace，积累到一定数量再决定
  补模板还是换路线。
- **判据**：`task-compiler` 组的"没有专用模板时用通用模板并记警告"。

### P-19 计划里的能力表还写着 `scoring` 族

- **现象**：Phase 5 的映射表写 `scoring_evaluation → scoring、analysis、admet`，
  而 Phase 0.5 已经把 `scoring` 拆成 `docking` 与 `affinity`。
- **根因**：两张表写在不同阶段，拆族时没有回头改能力表。
- **解决**：`scoring_evaluation` 用 `affinity、analysis、admet`，**不带 `docking`**——
  它做的是对已有产物的独立评分，重新对接不属于它的职责；`virtual_screening`
  才同时需要 `docking` 与 `affinity`。
- **判据**：`tools/check_capabilities.py` 的族名校验；`capabilities` 组的角色反查。

### P-20 `family_tokens` 的参数名有歧义，接错会静默返回 1

- **现象**：写能力判据时把**族名**传给 `family_tokens`，每个角色都显示"约 1 token"。
- **根因**：参数叫 `names`，实际收的是**工具名**；传族名时一个都不匹配，
  `json.dumps([])` 就是 1 token，看起来像一个正常的数，不报错。
- **解决**：参数改名 `tool_names`，文档写清"传工具名，不是族名；要族名先经
  `catalog()` 换"。判据脚本改成先展开成工具名。
- **判据**：`tools/check_capabilities.py` 输出的每个角色成本量级正常
  （1,595–8,263 token，而不是 1）。

### P-21 意图类型名与能力名不是同一套

- **现象**：路由把 `ligand_discovery` 当成能力名去查表，查不到，被当成"不认识
  的标签"跳过——整段配体能力从计划里消失，只留一条警告。
- **根因**：Phase 2 的意图类型与 Phase 5 的能力各起了一套名字
  （`ligand_discovery` 对 `ligand_intelligence`，`target_inquiry` 对
  `target_intelligence`），Phase 6 之前没有任何地方把它们对上。
- **解决**：模板里显式写 `capability`，不拿意图类型顶替。判据组 `router` 里加一条
  "每个模板的能力名都在注册表里"，防止下次改名再漏。
- **判据**：`router` 组的"能力名在注册表里存在"。

### P-22 前置关系不能按"能力都要有"写

- **现象**：`pocket_discovery` 被写成依赖 `structure_discovery`，于是正常的
  "找口袋"任务一编译就报"缺 structure_discovery 的产物"。
- **根因**：把"流程上通常先取结构"当成了"缺了它做不了"。实际上口袋发现自己的能力
  里就有 `structure` 族，能自己取结构。
- **解决**：前置只写**下游确实没有产出该产物的工具族**的情况。现在只剩四条：
  口袋画像依赖口袋发现、筛选依赖口袋与配体、评分依赖筛选、机制依赖画像与配体。
- **判据**：`router` 组的"前置齐全时没有未决"。

### P-23 按子目标取族只对多能力角色有效

- **现象**：`mechanism` 是单能力角色，按子目标裁剪之后仍是四个族、8,263 token；
  比核心工具还多。
- **根因**：裁剪的粒度是"角色下的能力"，单能力角色没有可裁的余地。
- **解决**：本轮不处理。要真正降下来，得把能力再拆细（例如"机制-残基"与
  "机制-构效"），或者把 `analysis` 这一个大族拆开。这两件事都会改 Phase 5 的表，
  留到 Phase 6 的后续迭代或 Phase 9。
- **判据**：暂时没有；`tools/check_capabilities.py` 会把 8,263 这个数一直报出来。

### P-24 状态文件是 TOML，存不了 None

- **现象**：给会话加 `task_spec` 字段后，全量测试在保存状态时崩：`Object of type
  'NoneType' is not TOML serializable`。
- **根因**：`to_dict()` 直接写了 `None`。TOML 没有 null，只有省略键或空表。
- **解决**：写空字典 `{}`，读的时候把空字典还原成 `None`。判据里补了往返检查。
- **判据**：`route` 组的"任务规格记在会话上"；全量测试里的状态保存条目。

### P-25 路由失败时不能写状态（fail-closed）

- **现象**：一开始只要 `decision.families` 非空、模式是 enforce 就装族，即使这次
  路由带着错误。等于把一份半成品计划写进会话，下一轮按它继续。
- **根因**：把"有结果"与"结果可用"混为一谈。
- **解决**：只要 `decision.error` 非空，trace 照写（route.plan 保留证据），但**不改
  任何会话状态**：不写任务规格、不装族。下一轮仍按原来的路径走。
- **判据**：`route` 组的"路由出错时不装族""路由出错时不写任务规格"。

### P-26 shadow 也写任务规格，这本身是一种影响

- **现象**：shadow 要求"只记录、不改变执行"，但如果不写 `task_spec`，下一轮就没有
  当前任务可继承，"继续""改目标"永远判不出来，样本全是 `new_task`。
- **根因**："不改变执行"与"不改变状态"不是同一件事：任务规格不参与工具清单，
  但它参与下一轮的解析输入。
- **解决**：shadow 写任务规格，但**不装族、不改工具清单**。这一点写进
  `route_adapter.py` 的模块说明，避免以后有人把它当成纯粹的只读观察。
- **判据**：`route` 组的"shadow 不改工具清单""shadow 也记任务规格"。

### P-27 `Verdict` 与权限层重名，导入互相遮蔽

- **现象**：循环层同时 `from .permission import Verdict` 与 `from .validators import
  Verdict`，后者的名字被前者覆盖（或反之），运行时 `Verdict()` 报
  "EnumType.__call__() missing 1 required positional argument"。
- **根因**：两个模块各有一个叫 `Verdict` 的类型，含义不同（权限结论 / 校验发现汇总）。
- **解决**：循环层只导入 `check_tool`，不再导入校验器的 `Verdict`；返回类型标注用
  `Any`。跨层同名词是这类问题的源头，能不同名就不同名。
- **判据**：全量测试；`validators` 组。

### P-28 enforce 下被拦要用"工具失败"写回，不能抛异常

- **现象**：校验器判 deny 时，若直接抛错，整轮会中断，模型也看不到原因；用户只看到
  一条退出信息。
- **根因**：把"这一步不允许"与"这一轮失败了"混为一谈。
- **解决**：与钩子拦截走同一条路——`_fail_tool` 把原因写进工具结果，模型下一步能看到
  并改道；本轮继续。trace 里另发一条 `validator.finding`。
- **判据**：`validators` 组的"enforce 下计划外的工具被拦"（工具状态 failed、输出含原因）。

### P-29 交付物名与登记表句柄之间没有对应关系

- **现象**：模板要求交付 `PocketCatalog`、`CandidateSet`，登记表里存的是
  `ligandset#1`、`artifact#2`；两边没有名字上的联系，交付校验无从下手。
- **根因**：Phase 4 的模板按"科研意义上的交付物"命名，登记表按"工具产出的对象"
  命名，中间少了一层映射。
- **解决**：新增 `validators/output_contract.py`，逐个写明怎么验：`handle`（登记表
  里有没有这一类条目）、`path`（工作区里有没有这个目录）、`manual`（无法机械验证）。
  现在能机械验的只有两件：候选集要配体集、评分报告要有运行目录；其余九件是报告
  类，标成 `manual`，交给评审。
- **判据**：`delivery` 组的"每个交付物都有合同""报告类标成无法机械验证"。
- **遗留**：九个 `manual` 交付物意味着交付验收目前只能抓两类缺失。要真正提高覆盖率，
  得让工具在产出时登记带名字的条目（例如 `artifact` 的标签就是交付物名），那是
  Phase 9--11 的事。

### P-30 交付验收为什么不阻断

- **现象**：轮末发现少交了一件，此时回答已经发给用户了，拦也拦不住。
- **根因**：验收发生在"答案已经产生"之后，缺少"补交一轮"的机制。
- **解决**：这一步只记录（`validator.delivery` 事件），不改退出原因、不追加提问。
  真要阻断，需要一轮"按缺失清单补交"的循环，属于独立设计，留待 Phase 9 的报告
  协议一起做。
- **判据**：`delivery` 组的"轮末写一条交付验收事件"。

### P-31 报告要求与 `AgentReport` 的构造校验有重叠

- **现象**：`AgentReport` 已经规定"标 completed 就必须有 findings 与 conclusions"，
  Profile 若再要求一遍，同一件事会有两条说法。
- **根因**：协议的构造校验与角色的附加要求没有分界。
- **解决**：Profile 的 `report_requirements` 只管 `evidence_refs`、`artifact_refs`、
  `limitations`、`unresolved_questions` 四项，别的字段交给协议本身。两层的分工写进
  `profiles.py` 的模块说明。
- **判据**：`profiles` 组的"坏说明书要被拦住（不认识的报告字段）"。

### P-32 报告不调模型，那"结论"从哪来

- **现象**：计划要求子 Agent 交结构化报告，但没说报告内容由谁写。让子 Agent 再调
  一次模型来总结，等于把它刚读过的原文重新发一遍，省下的上下文又花回去。
- **根因**：报告的目的是压缩，而"用模型压缩"和"用模型生成"是两件事，前者不必
  再看原文——原文已经在会话里了。
- **解决**：`reports.py` 只做机械抽取：结论取最后一条助手正文按行拆，产物取登记
  表里成功调用留下的 `receptor#` / `ligandset#` / `artifact#` 句柄，证据取正文与
  工具输出里的链接，局限取失败的工具与退出原因。抽不出就留空，由
  `profile.check_report()` 判不合格退回，不补写。
- **判据**：`reports` 组的"结论按行拆开并去掉列表符号""证据取正文里的链接并去掉
  句末标点""空回答抽不出结论，不编"。
- **取舍**：机械抽取会漏掉措辞上的归纳，只保留原文里写明的句子。这是有意的：
  父会话要的是可追溯的句子，不是二次概括。

### P-33 没有回答却标 completed，会交出一份空报告

- **现象**：子会话可能因为"模型直接收尾、没写正文"而正常结束，此时 `last_exit_reason`
  为空，按退出原因判就是 `completed`，但结论是空的。
- **根因**：状态是从"为什么停下"推的，不是从"交出了什么"推的。两者在正常情况下
  一致，在异常收尾时不一致。
- **解决**：`completed` 且没有结论时降成 `partial`。协议允许 `partial` 带空结论，
  父会话据此知道这份报告没说完，可以要求补交。
- **判据**：`reports` 组的"空报告不标完成"。

### P-34 报告模块按包内相对路径导入，运行时找不到模块

- **现象**：`reports.py` 写成 `from .models import ...`，导入时报
  `ModuleNotFoundError: vsagent.core.agent.models`。
- **根因**：`reports.py` 在 `vsagent/core/agent/` 下，`models.py` 在 `vsagent/core/` 下，
  少退了一层。
- **解决**：改成 `from ..models import ...`。同类问题在 `profiles.py` 没有出现，
  因为它只依赖 `capabilities.py`（同目录）。
- **判据**：`reports` 组能导入并跑通，全套 4,330 项通过。

### P-35 "工具集合不超过授权"写在说明书里，判在哪一步

- **现象**：Phase 9 的验收要求"子 Agent 的工具集合不超过 Profile 授权范围"，但
  说明书只写到族与动作类，没有说谁在什么时候核对。等到子 agent 跑起来才从
  工具调用里发现，已经花掉一轮上下文。
- **根因**：授权范围是静态声明，越权是派发时的决定，两者之间缺一个判据。
- **解决**：`AgentProfile.check_task(task, families)` 在派发前核对两件事：任务的
  动作类（`permissions`）与要装的工具族都必须在说明书里。返回问题清单，与
  `check_report()` 同一形状（空列表表示通过），调用方不用写两套分支。
- **判据**：`profiles` 组的"授权范围内的任务可以派""没授权的动作要拦下"
  "没授权的工具族要拦下""派错角色要拦下"。
- **遗留**：调用点在 Phase 10 的派发处。现在只有判据，没有调用方——这是有意的：
  Phase 9 定义规则，Phase 10 才产生派发。
- **未做的两项**：说明书里的 `timeout / retry` 与按角色加载的 system prompt。
  前者要等调度器（Phase 10）才有消费者，后者按设计稿排在 Phase 10 的规则分层，
  现在加字段只会是无人读取的配置。

### P-36 子 agent 的报告怎么回到父会话

- **现象**：原计划是"跑完把摘要写进父会话的一条 AGENT Part"。真去看渲染与上下文
  装配才发现：AGENT Part 只用于显示，`translate_message` 只认 TEXT / FILE ——
  写进父会话的消息列表，父会话的模型看不到；要看就得让父会话再问一次。
- **根因**：把"界面上看得见"当成了"模型看得到"。两者是两条通道。
- **解决**：报告走**拉**的路径，不走进消息列表：`AgentDispatcher.collect()` 按需
  生成，`agent_status` 在子会话有角色时补一段"报告：合格 / 不合格（缺什么）+
  产物句柄 + 证据"。父会话要结果就调 `agent_status`，与原来取结论是同一条路。
  不主动推一条消息进去，是因为那会在模型没要求的时候占用窗口——正是报告机制
  要避免的事。
- **判据**：`dispatch` 组的"合格的报告在 agent_status 里标合格""不合格的报告明说"
  "没有角色的子会话不加报告段"。
- **遗留**：串行链路里上游的 `artifact_refs` 由调度器直接写进下游任务的
  `input_refs`，不经聊天记录。这一步在调度器（下一步）。

### P-37 任务号判重不能另存一份映射

- **现象**：最直接的做法是维护 `task_id → session_id` 的字典。它重启就没了，
  而子会话上的 `task_id` 会跟着状态文件留下来，两份记录一旦不一致，
  重启后会为同一个任务再建一个子会话。
- **根因**：判重需要的是"这个任务派过没有"，这个事实已经在子会话上了。
- **解决**：`find()` 直接扫本会话的子会话，按 `task_id` 比对；字典只当快路径的
  位置也不留。任务号为空（自由文本派发）时直接返回 None，不参与判重。
- **判据**：`dispatch` 组的"第二次派发不新建""同一个任务号只调一次 spawn"。

### P-38 同一个任务号换了角色要拒绝，而不是复用

- **现象**：任务号相同、角色不同，可能是重规划时改错了角色，也可能是复制粘贴
  漏改任务号。两种情况都不能悄悄复用已有的子会话。
- **根因**：任务号是"这一份任务"的标识，角色是它的一部分；只对号不对角色，
  会让一份结构与口袋的任务被当成配体任务的结果交上去。
- **解决**：`dispatch()` 发现已有会话的角色与本次不同就抛 `DispatcherError`，
  并说明"先给这次改动作换一个新任务号"。
- **判据**：`dispatch` 组的"拒绝时说清是哪个任务号"。

### P-39 上游报告不合格，下游要不要停

- **现象**：上游跑完了，但报告按角色判不合格（缺出处、缺产物）。下游依赖它，
  按"失败就卡住"的写法会一起停；按"完成就放行"的写法又会让下游拿着空引用开工。
- **根因**：把"跑完了"与"交的东西合格"当成了一件事。它们分开时，停与不停都不是
  显然的答案。
- **解决**：给调度结果加一个 `partial`：跑完了、报告不合格、但**不拦下游**。
  理由是它缺的通常是一句出处，而不是产物；真要重做，调用方按 `problems` 决定，
  调度器不替它拿主意。状态记成 `blocked` 只留给"上游真的失败或中断"。
- **判据**：`scheduler` 组的"缺产物与证据的报告算 partial""上游 partial 不拦下游"。

### P-40 任务状态不写回 `AgentTask`

- **现象**：最顺手的写法是跑完把 `task.status` 改成 `done`。但 `AgentTask` 是计划
  的一部分，同一份计划重跑时还要用；写进去之后第二次跑就带着上一次的痕迹，
  幂等判重也会被它带偏。
- **根因**：任务对象同时承担"计划里的节点"与"这一次的执行记录"两个角色。
- **解决**：状态只记在 `Schedule.outcomes` 里，`AgentTask` 保持只读。要持久化
  就由调用方把 `outcomes` 写成事件或账本条目，那是另一个决定。
- **判据**：`scheduler` 组的"四个任务"那一组跑完后，输入的 `tasks` 列表内容不变
  （调度器里没有任何写任务对象的语句）。

### P-41 缺依赖与成环是两个毛病，不能报成一条

- **现象**：`b` 依赖一个不存在的任务，第一版分层把这条边算进去，于是 `b` 永远
  排不出来，问题清单里同时出现"依赖不存在的任务"和"依赖成环"。
- **根因**：分层用的是全量依赖边，而"不存在的任务"本来就不该成为一条边。
- **解决**：建图时先把指向不存在任务的依赖剔掉再分层；两个问题各报一条，
  互不牵连。
- **判据**：`scheduler` 组的"缺依赖只报一条，不跟着报成环"。

### P-42 任务号必须可复现，不能随机生成

- **现象**：协调器给每个角色建一份任务，最省事的做法是随机编号。那样每次重跑
  都得到新任务号，派发器的幂等判定形同虚设——同一份计划跑两遍会建两套子会话。
- **根因**：幂等的前提是"同一条任务两次得到同一个号"，而随机号让这个前提不成立。
- **解决**：`task_id = f"{plan.task_id}:{role}"`。计划号在一份任务里稳定，角色在
  一份计划里不重复，两者拼起来既唯一又可复现。要重跑就换计划号，不靠碰运气。
- **判据**：`coordinator` 组的"任务号由计划号与角色拼出来""重跑不重复建会话"。

### P-43 交付物只给最后一环，多终点时不硬分

- **现象**：模板里的 `required_outputs`（`CandidateSet` 之类）是整个任务的结果，
  不属于中间的每一步。平均分给每个角色，等于让中间环节也为最终交付物负责，
  报告判定会一起变严。
- **根因**：能力表里没有"哪项能力产出哪个交付物"的映射，硬编一张表就是新造一份
  没有依据的配置。
- **解决**：按"没有下游的角色"（汇点）分配。只有一个汇点时它领全部交付物；
  汇点不止一个说明计划有多个终点，硬分会把同一件交付物挂到两份任务上，
  于是不分配、只告警，由调用方决定怎么归。
- **判据**：`coordinator` 组的"交付物挂给汇点""多个终点时不给任何任务挂整份交付物"。

### P-44 计划里的依赖是角色，任务里的依赖是任务号

- **现象**：`CapabilityPlan.dependencies` 写的是 `{"from": "structure_pocket",
  "to": "screening"}`，而 `AgentTask.dependencies` 要的是任务号。直接传过去，
  调度器会认为依赖指向不存在的任务。
- **根因**：两层描述的对象不同——计划描述"谁等谁"，任务描述"哪一份等哪一份"。
- **解决**：翻译时按 `task_id_for(plan, role)` 换成任务号，同一个角色在计划里
  只有一份任务，所以这个换算是确定的。
- **判据**：`coordinator` 组的"角色依赖换成任务号"。

### P-45 加第二个常驻工具，把预算余量一次用完了

- **现象**：`dispatch_campaign` 加进来之后，主 Agent 的常驻工具从 7,818 涨到
  7,955，上限 8,000 只剩 45 token。第一版说明写了 176 token，直接把余量吃光还
  差一点；压掉两句举例之后才通过。
- **根因**：预算本来就只有一百多 token 的余量，一个新工具的量级正好是它。
- **解决**：说明压到 137 token（去掉"结构与口袋、配体、筛选等"这类举例——工具
  列表里本来就有），判据通过。**没有删任何工具**，等于承认余量用完了。
  设计稿里补了一句：下一个常驻工具必须先合并或删掉一个现有的。
- **判据**：`tools/check_toolset.py`（主 7,955 / 8,000）、`core-tools-profile`
  组的"常驻工具按清单装配：21 个"。

### P-46 战役不能塞进 `_tasks`

- **现象**：最省事的做法是复用 `_start` 起后台任务。但 `_tasks` 的语义是"这个
  会话有一轮回答在跑"，`is_running`、`prompt` 的互斥、界面状态都按它判。
  一场战役持续几分钟，塞进去会让"正在回答"一直为真。
- **根因**：两个生命周期不同的东西共用了同一个登记表。一轮回答以最后一个
  token 结束，一场战役以所有子会话跑完结束。
- **解决**：单开 `_campaigns`，配 `start_campaign` / `campaign_running` /
  `cancel_campaign`。同一个会话同时只允许一场，重复发起返回 False。
- **判据**：`campaign-dispatch` 组的"战役在跑""取消之后战役不再运行"。

### P-47 结果写回任务状态只能追加

- **现象**：`TaskState.apply` 的 `done` / `todo` / `blockers` 是**整段替换**。
  战役结束直接写一份新的进去，模型此前自己记的进度会被悄悄抹掉。
- **根因**：同一个字段有两个写入方（模型记进度、战役记结果），语义却没约定。
- **解决**：写回时先读现有列表、追加不重复的条目，再一次 `apply`。战役只加不减；
  要清理由模型或用户来做。
- **判据**：`campaign-dispatch` 组的"完成的角色写进任务状态""失败的角色写进卡住"。

### P-48 取消战役不能连坐用户自己派的子 agent

- **现象**：取消战役时把所有子会话一起停，会把用户用 `/agent` 建的那些也停掉。
- **根因**：`children_of` 只回答"谁挂在它下面"，不区分是谁派出去的。
- **解决**：只停带 `task_id` 的子会话——那是结构化派发写的标记，自由文本派发
  留空。返回值是停掉的会话数，调用方据此知道有没有东西真的被停。
- **判据**：`campaign-dispatch` 组的"取消战役连子会话一起停"。

### P-49 科研对象的 ID 由身份决定，不由登记顺序决定

- **现象**：设计稿要求"同一结构、口袋、配体在不同 Agent 之间用相同 ID"。用自增
  编号做不到：两个 Agent 各自从 1 开始数，`structure#1` 在两边指的是不同的结构。
- **根因**：编号是登记顺序的副产物，不是对象本身的属性。
- **解决**：ID 一律 `类别:身份键`，身份键挑稳定且唯一的那一个（结构用 PDB 号、
  靶点用登录号、配体用 ChEMBL 号、口袋用"受体 + 第几个"）。结构和登录号按大写
  规整，`4hjo` 与 `4HJO` 是同一个对象。ID 与身份键对不上时构造就报错。
- **判据**：`research-workspace` 组的"结构编号按大写规整""同一个身份键只占一条"。

### P-50 证据等级不能事后改

- **现象**：同一条证据先按 `prediction` 登记，后来又按 `experimental_activity`
  登记一次，对象表里就会出现两条互相矛盾的记录，或者后一条把前一条覆盖掉——
  两种都让"这条结论的依据有多强"没法回答。
- **根因**：等级是证据的属性，不是登记动作的属性；同一份证据只该有一个等级。
- **解决**：同一个身份键再次登记时，等级不同直接报错，并说明"要更正就换一个
  身份键"。换键之后，旧记录还在，口径改过这件事留得下痕迹。
- **判据**：`research-workspace` 组的"同一份证据不能换等级"。

### P-51 只有实验级证据能改假设状态

- **现象**：评审最容易被写成"有支持证据就标 supported"。可对接分数、口袋预测
  这些计算预测也能"支持"一条假设，于是模型自己算出来的东西把自己证实了。
- **根因**：支持与证实被当成了同一件事。
- **解决**：`_decide()` 只认 `experimental_activity` / `experimental_structure`
  两类能写 `supported` / `refuted`；其余情况给 `defer`（不动状态）或
  `inconclusive`（写"判不了"），并在理由里写明最强证据是什么、缺什么。
- **判据**：`hypothesis-review` 组的"只有预测时不下结论""弱证据不改假设状态"
  "实验级反证优先"。

### P-52 停用对象不能删除

- **现象**：切换受体或换掉一个口袋之后，旧对象"没用了"，最直接的处理是删掉。
  但已经交付的结论里引用过它，删掉之后那条引用就指向空。
- **根因**：把"不再使用"与"从未存在"混成一件事。
- **解决**：`retire()` 只把状态改成 `retired`，对象留在表里；工作区索引不再列它，
  但按 ID 仍然查得到。真要清理是另一个动作，需要先确认没有结论引用它。
- **判据**：`research-workspace` 组的"停用不删除""停用的对象不进索引"。

### P-53 工作区必须按家族共享同一个实例

- **现象**：四个工具都声明"要一份工作区"。最省事的写法是每次调用现建一个
  `ResearchWorkspace` 再 `load()`——内容看起来总是对的，但两个子 Agent 同时登记时，
  后保存的那一份会把前一份**整份快照**覆盖掉（落盘是整份写的，不是追加）。
- **根因**：工作区是"这一件事"的共享状态，不是"这一次调用"的临时对象。
- **解决**：`AgentHost.workspace_for(session)` 按 `family_id` 缓存，父子会话拿到
  同一个实例；根会话删掉时 `drop_family()` 把它一起清掉。与 `ledger_for` 同一套
  理由与同一处收口。
- **判据**：`research-tools` 组的"子 agent 与父会话共用同一个工作区实例"
  "根会话删掉后缓存也清掉"。

### P-54 工作区走单独的内核注入口，不挤进登记表

- **现象**：工具需要的东西已经很多（登记表、任务状态、会话、证据、子 agent 运行时、
  事件、注册表）。工作区看起来可以塞进登记表那个口子。
- **根因**：两者回答的不是同一个问题——登记表回答"这一轮算出来的东西在哪"，
  工作区回答"我们在研究什么"。一个结构对象可以引用 `receptor#1`，反过来不成立。
- **解决**：`Tool.workspace_argument` 单列一项，由 `AgentLoop.workspace` 转交；
  声明了却没拿到时报"内核装配问题"，与其余几个口子同一条规矩。
- **判据**：`research-tools` 组的"漏传工作区时报装配问题"
  "循环层拿到的就是这一份工作区"。

### P-55 实验级证据必须带出处

- **现象**：模型可以调用 `add_evidence` 把任何一句话登记成 `experimental_activity`，
  评审随后就能凭它把假设标成"已证实"。文字上，编造的实测值与真的实测值一模一样。
- **根因**：等级是自我声明的，没有任何机械约束。
- **解决**：实测活性、实验结构、用户数据这三类**必须带至少一个引用**（数据库编号、
  DOI/PMID、产物 handle、数据文件路径），拿不出出处的只能按 `prediction` 或
  `inference` 记。引用不能证明数据为真，但能让复核有地方可去，也让"编一个实验"
  多出一道明确的动作。
- **判据**：`research-tools` 组的"没有出处的实测结果不算证据"。

### P-56 `research` 族跟着 `evidence_refs` 走

- **现象**：新族要挂到哪些角色上，凭直觉会挂给"做实验的那几个"。可报告要求
  `evidence_refs` 的角色有七个，只挂给其中三个，另外四个照样要引用证据却没法把
  证据登记成对象。
- **根因**：这一族的归属不是按"谁做计算"分的，是按"谁要交代出处"分的。
- **解决**：凡报告要求 `evidence_refs` 的角色都配 `research` 族（target、
  structure_pocket、ligand、literature、scoring、mechanism、hypothesis）；
  `conformation` 与 `screening` 只要求产物路径，不配。这条规则写进
  `capabilities.py` 的模块说明，加角色时照它判。
- **判据**：`capabilities` 组 + `tools/check_capabilities.py`（十个能力、九个角色
  全部通过）；`router` 组的"族按子目标取"。

### P-57 常驻工具额度只剩 18 token

- **现象**：新增一族之后，`load_tools` 的说明里多一行族清单，常驻工具从 7,955
  涨到 7,982，离 8,000 只剩 18 token。设计稿原先那句"下一个工具必须合并或删除一个"
  已经从建议变成了硬约束。
- **根因**：族清单写在 `load_tools` 的定义里（这样模型不用先装族就知道有哪些族），
  所以每加一族都会涨常驻工具这一段。前缀那 1,798 token 不受影响——两处分开计量。
- **解决**：这一次不裁剪——`research` 族只加了 27 token，判据仍通过。后续任何
  常驻工具的说明变长都会顶破上限，先合并再新增。
- **判据**：`tools/check_toolset.py`（主 7,982 / 8,000、子 4,240 / 4,800）、
  `core-tools-profile` 组。

### P-58 流水要记「出自哪次任务」，但不能让每步都长一串编号

- **现象**：设计稿要求 `Event` / `Step` 记 `task_id`、`agent_task_id`、
  `artifact_refs`。前两项当时没有；第三项其实就是已有的 `artifacts`（从
  `tool_meta` 抽出来的 handle 与文件路径）。
- **根因**：一场战役有一个计划号，里面每个专业 Agent 各有一个任务号，两级都要有
  才回答得了"这条结论出自哪次战役、哪一路做的"。只记任务号要再拆前缀，只记计划号
  分不出是哪一路。
- **解决**：`Step` 加 `task_id`（计划号，根会话退回任务规格号）与 `agent_task_id`
  （子 Agent 的任务号），由 `event_log.task_tags(session)` 从会话现取，不额外传参；
  事件不另存，按 `actions` / `artifacts` 同一套办法从流水聚合。展示只放在
  `recall_event` 的抬头一行——每步印一遍同一串编号只会把流水挤长。
- **判据**：`event-log` 组的"根会话的步记下任务规格号""子 Agent 的步同时记下战役号
  与自己的任务号""事件从流水里聚合出任务号""召回时看得到出自哪次任务"
  "旧记录没有这两个键时读成空串"。

### P-59 任务书要写明这次该装哪几族

- **现象**：子会话继承的是父会话**当时装过**的族。任务书里写着"报告里不能空：
  evidence_refs"，可它手上不一定有 `research` 族——做不到，又不知道缺什么。
- **根因**：族是随会话走的运行期状态，任务书是静态文本；两者原先没有交口。
- **解决**：`_task_book` 多一段"工具族：…（没装过的先用 load_tools 装）"，取派发时
  给的族，没给就用角色说明书里的全部族。
- **判据**：`dispatch` 组的"任务书写明这一族要装"。

### P-60 假设状态变化记在流水里，不另开一条总线事件

- **现象**：Phase 11 的验收有一条"假设状态变化有事件记录"。最直接的做法是让
  `review_hypothesis` 往总线上发一条 `hypothesis.updated`。
- **根因**：本仓的约定是**工具不发总线事件**——只有循环层与 host 发。工具是
  "这一步做了什么"的执行者，事件是"这一轮发生了什么"的叙述者，混在一起之后
  事件顺序就不再由循环层唯一决定。
- **解决**：状态变化由流水里的那一步记录（`review_hypothesis(hypothesis=…,
  apply=True)`，结果行写"已写回任务状态"），事件封存后 `recall_event` 能按
  任务号翻回这一步；界面直接读 `session.task_state`。不为这一件事破一次分层。
- **判据**：`research-tools` 组的"apply 才写回""状态改成 supported"；
  `event-log` 组的任务号关联。

### P-61 角色规则进前缀，阶段规则进任务层

- **现象**：设计稿要求把规则分成四档。最省事的做法是四档全部拼进稳定前缀。
- **根因**：角色在一次会话里不变，阶段会随子目标推进而变。全部进前缀，每推进
  一步前缀就变一次，整段提示缓存作废；全部进动态层，则每一步都要重算那些本来
  不变的内容，等于把常量当成变量发。
- **解决**：全局与角色进稳定前缀（`stable_prefix`），阶段进任务层
  （`context._stage_block`），参考只列名字、不读正文。阶段取自任务规格里的子目标，
  不取自模型自述；认不出的能力不硬塞进相邻阶段。
- **判据**：`rules-tier` 组的"阶段规则不进稳定前缀（每推进一步就变，会把缓存打掉）"
  "阶段规则随任务状态进了动态层""没有阶段时整段不出现"；
  `tools/check_prefix.py` 的"每一步最多 1,035 token（全局 + 一份角色 + 一份阶段）"。

### P-62 分级规则也进模型视野，「不点名看不见的工具」要扩过去

- **现象**：`tools/check_prefix.py` 原先只查内置纪律与 `AGENTS.md` 里有没有点名
  首步不可见的工具。新增的十三份分级规则不在检查范围里。
- **根因**：其中三份全局与十份角色会进前缀，五份阶段会进任务块，模型都看得到。
  写进去的领域工具名与内置纪律里的一样，会让模型去装它当时装不到的族。
- **解决**：把全局、角色、阶段三层拼成一段一起查；参考材料排除在外——它们不注入，
  本来就该点名具体工具。同时核对目录与代码里的名单：角色多一份、阶段少一份都报错。
- **判据**：`tools/check_prefix.py` 的"分级规则里点名了领域工具"（当前为空）、
  "这些角色没有规则文件""这些阶段没有规则文件"；`rules-tier` 组的目录核对。

### P-63 角色规则与说明书两处都写「这个角色负责什么」

- **现象**：`profiles.TITLES` / `NOTES` 已经写了每个角色的定位，
  `rules/agents/*.md` 又写了一遍。两处各改一半，就会出现说明书说只读、
  规则说可以写。
- **根因**：两处用途不同——说明书用于派发前核对授权（机器判），规则用于提示模型
  （人读），不能合成一处。
- **解决**：文件首行标题必须与 `TITLES[role]` 对得上，判据逐份比对；每份不超过
  400 token，超了说明它在往手册的方向长。
- **判据**：`rules-tier` 组的"规则标题与说明书一致""不超过 400 token"；
  `tools/check_prefix.py` 的同一条体量上限。

### P-64 战役状态机：状态是「当前是什么」，不是「发生了一次变化」

- **现象**：设计稿给了九格主链路与三条横切边，原先只有一个布尔
  `campaign_running`。它只回答「在不在跑」，回答不了「跑到哪一格、结果收齐了
  没有、用户改口之后手上这份计划还算不算数」。
- **根因**：布尔把「有没有后台任务」与「这件事走到哪一步」压成了一个值。
  前者随任务生命周期变，后者随任务规格变，两者不同步。
- **解决**：`campaign_state.py` 只放一张转移表与两个函数（`advance` 抛错、
  `soft_advance` 返回理由）；会话上记三个字段（状态、计划号、规格版本）。
  接线四处：路由编出规格时写「定规格」；派发工具写「排计划」「派发」并记计划戳记；
  host 写「研究进行中」「汇总结果」「已取消」「失败」；轮末在「汇总结果」之后
  写「复核」「已交付」。`agent_status` 报当前格与计划作废原因。
- **取舍**：终态之后当新一轮（不校验），终态之间互跳仍然拒绝；卡住可以回到任何
  进行中的格子；汇总之后允许直接补一轮研究，不必先走完交付。
- **判据**：`campaign-state` 组 61 项（链路、跳步、终态、卡住、戳记、往返、
  host 两头）；`campaign-dispatch` 组的四格；`route` 组的"编出规格就记定规格"
  "换了任务号回到定规格""汇总之后交付"。

### P-65 系统评测只能判结构，不能判好坏

- **现象**：设计稿列了十三项指标，要求与原单 Agent 基线对照。其中意图准确率、
  用户意图保真、证据覆盖率、产物可追溯率、成本与延迟，离线一个都量不了。
- **根因**：这些数要么要真实模型跑解析，要么要一场真实运行留下的报告与登记表。
  在没有这些输入时给一个数，就是把「没量」说成「量了」。
- **解决**：`tools/eval_system.py` 只判能机械判的八条结构不变量——约束保留、
  排除项保留、子目标覆盖、交付物落位、依赖有效、不重复派、工具暴露、
  未决输入有交代；其余五项列成清单，写明去哪儿量。脚本明确打印
  「Agent 数量、工具调用次数、输出长度不作为指标」。
- **取舍**：排除项那条只覆盖能力级排除（对接、筛选）。「不要引用预印本」这类
  来源质量要求不是能力，判不了，交给约束保留那条管——这一点写在脚本开头。

### P-68 打包产物旁边没有 `rules/`

- **现象**：分级规则从 `rules_directory(root)/rules` 读。打包后 `rules_directory`

  - `tests/test_agent.py --only packaging`（9 项）：spec 的 `datas` 引用了两条路径、

### P-75 工具命名统一与参数默认值

- **现象**：同样是「按编号取一条记录」，`fetch_target` / `fetch_structure` 用 fetch，
  `lookup_compound` 用 lookup；同样是「找一批相似的」，`search_actives` /
  `search_literature` 用 search，`find_analogs` / `find_similar_compounds` 用 find。
  模型在一堆近义动词之间没有稳定迁移路径。数值参数里则有一批只写「上限」不写范围与默认。
- **根因**：工具是按功能陆续加的，命名跟着当时的说法走；参数说明写的是「这个数是什么」，
  没写「不给会怎样」。
- **解决**：
  1. 三个工具改名，类名同步：`lookup_compound` → `fetch_compound`、
     `find_analogs` → `search_analogs`、`find_similar_compounds` →
     `search_similar_compounds`。调用点只有 `debug_tools.py`、测试与三处同包引用。
  2. 命名约定写进 `docs/design.md` §5.1：`search_*` 找一批、`fetch_*` 取一条、
     `list_*` 列清单、`screen_*` 从一批里筛；新工具照此落位。
  3. 参数按「有没有数字」重扫了一遍：359 个参数全部有说明；真正缺范围的是
     `curate_ligands` 的六项（分子量 0–2000、logP −20–40、TPSA 0–1000、HBD/HBA 0–50、
     可旋转键 0–100）与 `enumerate_analogs` 的两项（不给则不筛），已补齐。
     其余被判「弱」的参数多半是标识类，说明里已经写了来源或示例；JSON Schema 的
     `enum` 本来就把取值列给了模型，不在描述里重复。
- **不需要迁移**：`Session.tool_families` 存的是族名，族没有改；旧事件里的工具名只是
  历史文本，不会被重新调用。
- **判据**：全量 **4,679** 项通过；`tools/check_toolset.py` 常驻 20 个 / 7,953 token
  （预算 8,000）；`grep` 三个旧名在代码里为零（`runs/` 的历史产物与本文档除外）。

### P-77 派发子集与自定义任务书，删掉 `/agent`

- **背景**：用户只想要一个「口袋调查」的子 agent。`dispatch_campaign` 只能整份计划

     报错并列出计划里的角色；多角色 + `task` 直接拒绝。预演改成 `中文名（role）`，
     模型才知道该传什么。

  5. 测试：`subagent-ui` 改为直接调 `host.spawn`（含 `run=False` 的待开始流程）；

### P-78 意图解析与任务定义接入 TUI 与网页

- **问题**：前置流程（`_prepare_route`）的产出只落在 trace 与会话字段里，界面上看不见。

  都只有工具卡能展开，过程记录没有位置。
- **解决**：
  1. 新增 `PartType.ROUTE`，`route_adapter.describe(decision)` 把意图、任务规格、角色计划

     `coordinator → scheduler → dispatcher → host → loop` 会成环。

     解析失败也写（`意图与任务 · 未解析` + 原因），失败与成功都有交代。

### P-81 路由补前置闭包：计划必须自己可执行

- **来源**：查 ses_0035（2026-11-13，HA2 配体筛选）的派发失败。两次
  `dispatch_campaign(roles=["structure_pocket"])` 被「这些角色不在这份计划里」拒，
  一次 `roles=["screening"], task=…` 被「自定义任务书只在结果只剩一个角色时可用」拒；
  最后一步结构盘点在纯编排之后**没有任何会话能做**。计划本身只有
  `ligand_intelligence + virtual_screening`，而路由自己已经在 warnings 里写了
  「virtual_screening 需要 pocket_discovery 的产物」。
- **根因**：`PREREQUISITES` 缺了就只记 `unresolved_inputs`，没有任何一步把它补成节点；
  P-80 又把「缺前置」变成硬闸门——两边一起把这份计划变成**不可派发**，
  而闸门提示的「把缺的那一步加进计划」当时没有任何工具能做。
- **解决**：
  1. **分两类前置**。新增 `capability_router.AUTO_PREREQUISITES`：`virtual_screening`
     ← `pocket_discovery` + `ligand_intelligence`，`pocket_profiling` ← `pocket_discovery`。
     判据是**能不能花上一次的产物**：评分可以吃已有候选集，筛选不能凭空有口袋。
     补进来的节点排在依赖它的那一项前面，`denied` 里的不补（不能靠补节点绕开禁止项）。
  2. **补出来的节点要有任务书**。任务规格里没有对应子目标的角色，`build_tasks` 用
     模板里那句子目标兜底（`coordinator._template_goals`），不再只给一句
     「完成 pocket_discovery 这一段」。
  3. **确认点跟着能力走**。`plan.approval_points` 改成从选中能力反查模板
     （`_approvals`，按 `APPROVAL_ORDER` 排）；路由块优先用它，否则补出来的口袋阶段
     会在 `[任务]` 里漏掉「结合口袋确认」。
- **判据**：
  - `router` 组 44 项（+8）：`ligand_discovery + virtual_screening` 编译出的计划含
    `pocket_discovery`、三个角色 `ligand / structure_pocket / screening`、
    `structure_pocket → screening` 依赖边、`unresolved_inputs` 为空、告警写明补了什么、
    `missing_prerequisites() == []`（能过 P-80 的闸门）、确认点含「结合口袋确认」；
    反向判据：孤立 `scoring_evaluation` 仍然只有一个角色、不补 `virtual_screening`。
  - `campaign-dispatch` 38 项：缺前置的样本改用 `scoring_evaluation`（筛选已经补不出来了），
    「不可派发」与 `confirm=true` 拒绝照旧。
  - `route` 组 94 项、`dispatch` 67 项照常通过。
  - `tools/check_capabilities.py` 全过；全量 `tests/test_agent.py` 4,700 项、`EXIT=0`；
    冒烟 5,611 项、`EXIT=0`。
- **没做（用户只选了这一条）**：
  1. `roles` 收窄与自定义任务书互斥：`roles=["screening"], task=…` 因为自动补上游变成
     两个任务而被拒，报错还建议「用 roles 只选一个」——这是死路，`tests/test_agent.py`
     里那条断言把错误行为固化了。
  2. 计划中途不可修订：`_requested_roles` 只允许从计划里减，`continue_task` 又把同一份
     规格再路由一遍，主 agent 中途发现的阶段进不了计划。现在靠路由闭包预先把
     「必然要做的上游」补齐，但「计划外的角色」仍然派不出去。另外 `provided_inputs`
     没有口袋/配体的规范键，用户自带口袋时也会补一个口袋发现角色；等键定下来再按它抑制。
  3. 按 `roles` 子集派发时，战役 `done` 只列子集，计划里剩下的角色静默消失
     （等下一次派发才发现）；一轮 24 步在 33 次工具调用里用满，后 5 次调用被
     「本轮步数快用完了」拒掉，没有补救余地。
- **打包**：只改源码与 `tests/`，没重建 `dist/VSAgent`。

### P-84 代码结构：`core/agent/` 分五组，判据一条命令

- **起因**：`core/agent/` 根目录三十来个文件平铺，「谁能改计划」「谁在跑」「谁只是数据」
  全靠记文件名；改一个模块要在一屏目录列表里找。这是纯结构整理，**不改任何调用顺序**。
- **做法**：按「一个模块被谁用、什么时候被调」分五组——
  `planning/`（intent / intent_parser / task_context / task_compiler / capability_router /
  route_adapter / stages / context）、`roles/`（capabilities / profiles / toolprofiles /
  prompt / contracts/）、`execution/`（coordinator / scheduler / dispatcher / dependency /
  campaign_state / spawn / host / reports / report / loop / hooks）、
  `state/`（event_log / ledger / memory / hypothesis / hypothesis_review / history / task /
  topics / trace）、`research/`（research_objects / research_workspace / workspace /
  evidence_registry）。根上只留 `tools.py` / `toolset.py` / `coretools.py` /
  `permission.py` / `provider.py` 与 `domain/`、`validators/` 两个包。
- **import**：搬过的文件、以及指向它们的 import 一律改成绝对路径（其余相对 import 原地
  不动，免得整仓 diff 都是 `..` 换全路径）。89 个文件、329 行。
- **踩到的坑**：`roles/prompt.py` 里 `rules_directory()` 用
  `Path(__file__).resolve().parents[3]` 算仓根，搬深一层之后它指到 `vsagent/` 的上一层，
  规则文件读不到、`read_rule` 返回空串，**程序照常启动**——只有 `rules` 那一组判据红。
  改走 `core/paths.py:project_root()`，与层数无关。这是本次唯一一处非机械改动。
  另有两处不在扫描范围里的引用：仓根的 `debug_tools.py`（`context` / `ledger`），
  以及 `tools/report_session.py` 里一段网页注释的路径。
- **新增 `tools/check_all.py`**：按固定顺序跑 agent → smoke → capabilities → toolset →
  prefix → style → repo，任一条非零就停并打印末尾 40 行。`--list` / `--only <子串>`。
  理由：这些判据过去是「想起来才跑一个」，最常见的失败形态是根本没跑。
- **归档**：`docs/runtime-fixes-plan.md`、`-2.md`、`knowledge-center-plan.md` 移到
  `docs/archive/`（做完的计划，不随代码更新）；`review.md` 是活文档，留在 `docs/`。
- **判据**：`tests/test_agent.py` 4,752 项 `EXIT=0`（项数与整理前一致，`--only` 语义未变）；
  `tests/test_smoke.py` 5,663 项 `EXIT=0`；`check_capabilities` / `check_toolset` /
  `check_prefix` / `check_style` / `check_repo` 全 `EXIT=0`；`import vsagent.app` 通过。
- **没做**：`tests/test_agent.py` 拆成 `tests/checks/*.py`、`tools/` 再分目录——
  这两项只动组织不动行为，而前者要拆的是项目唯一的主判据（27k 行、共享夹具与
  `GROUPS` 注册表），拆坏的代价是**把安全网本身弄坏**。留作单独一轮。
  exe 挪出 `dist/` 同样没做：`rules_directory()` 的冻结分支按 `sys.executable` 的
  同级目录找规则，挪到 `dist/bin/` 就得再加一层回退，而验证它必须完整打一次包；
