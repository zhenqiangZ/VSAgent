# 真实会话里看到的失败模式

2026-10-25 两次真实会话（deepseek-flash / 1M 窗口），同一组三问：

1. 「查一下人 EGFR（P00533）在 PDB 里有哪些结构，挑一个带小分子抑制剂的给我编号」
2. 「把 4HJO 的结构取下来并登记成受体」
3. 「把 4HJO 写成一个运行目录，告诉我里面有哪些文件」

两次都跑完了，也都做成了；但同一组问题输入 **442K 与 135K**，差 3.3 倍。
差的那 3 倍几乎全在第 1 轮的步数上（24 步对 7 步）。这份文件只记账，不改代码：
每条写清现象、证据、根因在哪、代价多少，以及**是不是当初刻意的**——刻意的那些
要改就得连理由一起改。

| # | 现象 | 代价 | 根因位置 | 刻意？ |
| --- | --- | --- | --- | --- |
| F1 | `load_tools` 把被关掉的工具报成「已装入」，模型调它拿到「请改用别的办法」，于是 bash 自建 RCSB 客户端 | ~20 步 / 300K 输入 | `toolset.py:79`（列的是 `catalog()` 而非注册表）+ `loop.py:120`（禁用文案） | 否 |
| F2 | 模型在 Linux 上写 Windows 命令 | 2 步 | `bash` 工具的回执 | 否 |
| F3 | 猜错 handle 编号，`open_viewer` 失败 | 1 步 | 上下文里没有「当前有哪些 handle」的索引 | 否 |
| F4 | 模型不知道状态目录在哪，先试 `./.opencode_tui` | 2 步 | 上下文里没有工作目录 / 状态目录 | 否 |

## F1 · 装族说「装好了」，那个工具其实是被关掉的

**现象**：第 1 次会话第 1 轮，模型 `load_tools({"family": "rsearch"})`，工具回
「已装入 rsearch：search_pdb。下一步起这些工具出现在清单里」；下一步它调
`search_pdb({"query": "P00533"})`，收到的是「已被禁用……重试无用，请改用别的办法」。
它没有再试别的领域工具，而是 `bash` + `urllib` 自己写脚本拉 RCSB，连写三个
`.probe/*.py`，第 1 轮因此用满 `MAX_STEPS=24`。

**证据**：`.opencode_tui/tools.toml:12` 写着 `search_pdb = false`（同一份还关了
`search_literature`、`switch_receptor`）。装配时它们**不进注册表**
（`app._build_registry`），但 `LoadToolsTool` 列的是 `catalog()` 里的名字——
那是「有哪些工具」，不是「装进来了哪些」。于是它把一件永远装不进来的工具报成
「已装入」，模型照着这句话去调，撞上禁用清单。

两句原文可以复现：

```
load_tools 说： 已装入 rsearch：search_pdb。下一步起这些工具出现在清单里，参数按各工具的说明给。
模型看到的话： search_pdb 已被禁用（配置在 .opencode_tui/tools.toml 里，可在 /tools 面板里打开），
              本次会话不会提供这个工具，重试无用，请改用别的办法或告诉用户。
```

**为什么第一次归因错了**：我事后手动跑 `SearchPdbTool().execute({"query": "P00533"})`
拿到 391 条命中，就判成「那次是瞬时失败」。直调工具绕过了注册表，也就绕过了
禁用清单——它证明的是「工具本身好用」，不是「当时它被装进来了」。真正的判据是
注册表里有没有它：`registry.get("search_pdb") is None`。

**代价**：约 20 步、300K 输入。同一组问题两次跑，442K 对 135K，差的就是这一段。

**建议**：

1. **`load_tools` 减去禁用清单**。整族都被关掉时直接说「这一族里的工具都被项目
   配置关掉了，装进来也用不了」，而不是报「已装入」。这需要把注册表注入给它——
   `Tool` 已有声明式注入通道（`context_argument` / `task_argument` / …），
   加一个 `registry_argument` 即可，不必在 `run()` 里另想办法。
2. **禁用那句「请改用别的办法」是在教模型绕道**。第 1 次会话里它照字面做了：
   换数据源、自己实现。改成「不要用 bash 自己实现它，也不要换数据源绕过；要么让
   用户在 `/tools` 里打开，要么按用户指示继续」。

第 2 条单独也值得改：`search_literature`、`switch_receptor` 现在同样被关着，
同样的诱导会出现在任何一个被关掉的领域工具上。

## F2 · Linux 上写 Windows 命令

**现象**：第 2 次会话第 3 轮，模型执行 `bash("cd runs/4hjo && dir /s /b ...")`，
失败，改用 `ls -la` 才拿到文件清单。

**代价**：2 步。不致命，但它是「模型不知道自己在什么平台上」的直接证据。

**建议**：与 Phase 4 的 ENV 块合并解决——把平台写进上下文，比在 `bash` 的失败回执里
猜要稳。若 ENV 块一时不做，退而求其次：`bash` 失败且命令里出现 `dir`/`del`/`type`
时，回执补一句「当前平台是 linux」。

## F3 · 猜错 handle 编号

**现象**：第 1 次会话末尾 `open_viewer({"run": "artifact#2"})` 失败——当时登记表里
只有 `artifact#1`。模型是照前几步见过的编号推的，隔了几步就记串了。

**根因**：handle 只在**工具返回的那一刻**出现在上下文里，之后要么进了证据层、
要么随旧工具结果被清掉。模型要用的时候手里没有索引，只能凭记忆。

**建议**：Phase 4 的「产物索引」正好治这个——`SessionLedger.digest()` 给当前受体
+ 最近 5 个产物，≤10 行。这条不是锦上添花，是**上面这次失败的复现条件**。

## F4 · 不知道状态目录在哪

**现象**：第 1 次会话第 1 轮，模型执行
`bash("cd .opencode_tui/targets && python -c ...")`，失败（相对路径没有这个目录），
随后 `ls ~/.opencode_tui` 才找到。

**根因**：这次实验的状态目录在 `/tmp/vsa-lazy-session`，模型默认它在
`./.opencode_tui`。它没有「状态目录 / 工作目录是哪个」的任何信息，只能猜。

**建议**：并入 ENV 块（工作目录 + 状态目录 + 平台 + 日期）。注意必须放在
**易变区**：日期进了 `PREFIX` 就每天击穿一次缓存，还会红掉
「PREFIX 连续两步字节相等」那条判据。

## 已修 · 重试语义一直没接线

`RetryableToolError` 的 docstring 写着「与 `ToolError` 分开，是为了让重试逻辑只重试
这一类」，但 `loop.py` 的 `_execute_tool` 用 `except ToolError` 把它一起接住了——
**工具层一次都不重试**，那个标签等于白写。四处 `except Exception`
（`rsearch.py:253` / `:320`、`complexes.py:241` / `:332`）连标签都吃掉。
这两次会话里没有证据触发过它，但它与 F1 是同一个病：**说好要重试的东西没人重试**。

2026-10-25 接上：

- 循环层加 `except RetryableToolError`，重试 `MAX_TOOL_RETRIES = 1` 次，间隔用已有的
  `RETRY_DELAYS[0]`，界面发 `PartType.RETRY`（与模型请求重试同一个类型）。
- **只重试 `execute`**，不重跑权限与钩子：那两步是本地判定，用户已经点过允许，
  重跑只会把同一个问题问第二遍。
- 四处 `except Exception` 前补 `except RetryableToolError: raise`。
- 重试用尽的文案写明「不是参数错、不要用 bash 自己实现、不要换数据源绕过」——
  最后半句正是第 1 次会话缺的那句。
- 判据：`tests/test_agent.py --only tool-retry`，13 条，含「普通 `ToolError` 不重试」
  与「可重试错误能穿出 domain 层」。

为什么工具层只重试 1 次而不是 2 次（模型请求那层是 2）：一次工具调用的超时本身就有
几十秒，重试两次等于把一次网络抖动拖成三倍等待；工具失败之后模型还有别的路可走，
一次就够把「抖了一下」与「真的不通」分开。

## 不需要改的（正面证据）

- **按需加载不用教**：两次都自己 `load_tools`，按 structure → uniprot → rsearch →
  export（→ listing）装 4–5 族，没有一次需要提示。每步工具定义 3.1K → 6.0K，
  全量是 12.3K。装族那一步命中率 98.9% → 36.6%，下一步回到 95.9%——一次性。
- **说清下一步的失败文案是有效的**：第 2 次会话模型叫了 `search_pdb({})` 空参数，
  收到的是禁用文案（不是「至少要给一个条件」——那也是我事后直调才看到的），
  它没再纠缠，直接用已知编号取结构。同一个工具，第 1 次绕了 20 步、第 2 次一步没绕，
  差别在模型当时手上有没有别的路。
- **零命中不再被当成失败**（`EmptyResult` 那次修正）在这两次里没再触发误判。

## 按代价排序的修法

| 顺序 | 修什么 | 依据 | 风险 |
| --- | --- | --- | --- |
| — | 重试接线（**已做**，见上一节） | 说好要重试的东西没人重试 | 已补 `tool-retry` 判据 |
| 1 | F1-1 `load_tools` 减去禁用清单 | 它在**主动说谎**，模型只是信了 | 要加一个注入通道；判据可确定性写 |
| 2 | F1-2 禁用文案不再教绕道 | 20 步里至少一半是「请改用别的办法」买来的 | 纯文案，但有 3 个工具受影响，要一起看 |
| 3 | F3 产物索引 | 猜错 handle 是可复现的 | 无；纯增一层渲染 |
| 4 | F2 + F4 ENV 块 | 各 2 步，但是「模型对环境一无所知」的同一件事 | 位置放错会击穿缓存 |
