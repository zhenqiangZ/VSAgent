# 聊天界面设计（苹果设计原则）

本文记录 `ChatScreen` 的界面改造：设计理念、改造前的问题、逐条的修改方向与执行状态。
改代码的人先读这里，再读 `vsagent/screens/chat.py` 与 `vsagent/styles/app.tcss`。

**当前状态（2026-11-05）：七个部分与后两轮全部完成，第八节的左栏另加，判据全部通过。** 改到的文件：
`vsagent/app.py`、`vsagent/screens/{chat,home,permission,tools_panel}.py`、
`vsagent/core/models.py`、
`vsagent/widgets/{messages_pane,editor_pane,status_bar,toast,file_autocomplete}.py`、
`vsagent/styles/app.tcss`、`tests/{test_smoke,test_agent}.py`。剩下的两处记在第七节。

## 一、设计理念

取自苹果人机界面指南里与终端应用相关的那几条。

**内容优先。** 界面元素只在为用户服务时出现，用完就让位。留白把内容组织成组；能靠留白分开的两个区块，不再加线和标签标记。

**一个主调色。** 系统色用于交互与状态标记；一切不承载信息的装饰都取中性灰。屏幕上同时出现的强调色不超过一两种，否则没有任何东西看起来重要。

**直接操纵。** 能点的东西看上去就能点；按下的结果与预感一致；控件的位置、文字不只靠颜色传达状态。

**角色区别靠留白，不靠装饰。** 对话里谁在说话，用对齐、留白与字重区分；给每一方边框、标签或气泡，等于让装饰抢占内容的注意力。

**层级用明度与字重，不用色相。** 层次是重要到次要的过渡，用亮度差与字号差表达；用五种彩色区分五件事，读的人要额外学一套配色。

**控制与选项在需要时隐现。** 常驻的次要控件退成安静的文字或图标；选项收进一个地方，需要时再展开。

**连贯。** 同一个概念在界面各处长得一样，状态怎么表示、按键是什么反应，从头到尾一致。

## 二、改造前的问题

对照 `chat.py:314`、`messages_pane.py`、`editor_pane.py`、`status_bar.py`、`app.tcss` 的实际布局（100x30 实测：标题栏 1 行、消息区 22 行、输入区块 6 行、状态栏 1 行）。

1. **输入区块空着占 6 行，消息区只剩 22 行。** 空态输入区固定 3 行底高，加分隔线、间距、状态行，整块 6 行压在屏幕底部。
2. **标题栏、输入状态行、状态栏叠起来 8 行常驻装饰。** 三处都是低优先级信息，各占一行。
3. **同一类信息画了两遍。** 路径与分支、会话名、模型名、子 agent 状态都在两处以上出现。
4. **重复的强调色。** 亮蓝 `#4A9EFF` 同时用在用户消息边线、输入框指示线、Agent 名、侧栏分节标题、侧栏开关、子 agent 返回栏、收尾总结、命令模式边框、弹窗边框、工具省略行、新内容提示条。加上橙、绿、红、紫、琥珀、蓝灰，聊天界面同时出现八种色相。
5. **用户消息是占满整行宽度的气泡。** 一句话的提问铺满一百列，体量差距与内容重要性相反。
6. **工具卡片是多种图形的堆叠。** 展开标记、工具图标、状态中文词、耗时、权限说明、参数摘要串成一行，左侧还有按状态着色的竖线。
7. **状态信息在行内不加区分地混合。** `#editor-status` 四种颜色，`#status-usage` 把四项数字压成一簇。
8. **侧栏开关与 `/sidebar` 命令重复。**
9. **`── step N ──` 把实现细节推给用户看。**

### 额外修掉的一处时序问题

跟随状态按「这一刻的滚动量与最大滚动量」判定。视口在同一帧里变高变矮时，两个数对不上，
跟随会关着再也打不开。提示条修好之后（它占位与释放会让消息区在两行之间变一次），
这条路径上的问题稳定复现，五处一起改：

- `_resume_follow_at_bottom`：贴底直接恢复；差一行先再排一帧等夹回；看完这一帧仍然差一行
  就按到底处理。视口反向变高一行时滚动量停在这一行上不会再被夹回，一直重排只会永远
  差一行。`_at_bottom` 的容差本来就是一行，两处取同一个口径。
- `action_scroll_down`：滚动量没变的那一次也照排判读。贴底时最后一格往下滚不动，
  `watch_scroll_y` 不会被叫醒，排着的判读是唯一的收尾。
- `watch_scroll_y` 往上那一支：判读挪到这次刷新之后，等布局稳定再看落点。位置变小的
  那一刻 `max_scroll_y` 还是旧值，拿旧上限比会把「视口变高、位置被夹回」当成
  「用户往上翻」。
- `on_resize`：视口尺寸变了就再看一眼，落点还在底部就保持跟随。夹回不会触发
  「往下滚」的判读，最后一次按键排的判读可能已经跑过。
- 拖动滚动条：跟随状态由 `watch_scroll_y` 判，`ScrollTo` 带来的目标位置不参与。那个值
  是发消息那一刻按当时的最大滚动量算的，消息排到队尾才被处理时视口可能已经变过，
  拿它去比会把「拖到底」判成「没到底」。

`tests/test_smoke.py` 里滚到底的那条断言也补了一句等待：恢复跟随排在下一次刷新之后，
断言前要多等一帧，否则读到的是「已经贴底、回调还没跑」的中间状态。

核对过程中发现并修掉提示条的三处问题，改动在 `vsagent/widgets/toast.py` 与 `vsagent/app.py`：

- **看不见。** 正文没有写宽度，外层 `width: auto` 量到的是 0，整条提示被裁成 0 行——
  DOM 里有、屏幕上没有。正文改成 `width: auto; max-width: 100%`，短提示按文字宽度收窄，
  长提示在整屏 60% 处折行。
- **贴在左边。** 停靠只决定上下位置，左右由父组件的 `align` 决定，直接挂在屏幕上就顶到
  左边界。新增 `ToastRack`：铺满整行、靠右、竖向排列，提示条落在右下角，同时挂几条时
  往上叠；最后一条走掉时容器一起收掉，不留空行。
- **字形与正文之间不能留空格。** 折行按空格切词，字形后面跟一个空格就成了单独一个词，
  正文那一段整体放不进第一行剩下的宽度，被推到下一行——两行的提示占三行，第一行只有
  一个字形。字形直接接正文。

100x30 实测：一条十几个字的消息是十几列宽、一行高，贴着右下角；长消息在 60% 处折成
两行，右沿仍贴着屏幕右边。

## 六、第三轮：状态栏右端与提示条

### 状态栏右端改成占比数字

`#status-usage` 原来写的是「会话累计 token（占窗口百分比）· 费用 · 耗时」。累计值回答不了
「还能聊多久」——它只增不减，压缩上下文之后也不回落。改成最近一次请求实际带上的输入 token
除以窗口，只写百分比数字：

```
4%
```

`Session.last_input_tokens()` 取最后一条有用量的消息的 `tokens["input"]`：服务端记账的
prompt token，含工具定义与缓存命中的部分，也就是下一次还要再发一遍的那份东西。
还没发过请求时是 0。数字左右各留一格内边距，点开的命中区域不至于只有两个字符宽；
占比超过 60% 转黄、超过 85% 转红。状态栏保持 1 行高。

费用与累计用量挪到侧栏的用量段，按缓存命中、未命中与输出分开：

```
12 条消息 · 总 42.1K tokens
缓存命中 30.0K
未命中 8.0K
输出 4.1K · $0.12
```

输入分成命中与未命中，两者的单价差十倍，合成一个数就看不出省了多少。
耗时从界面上撤掉：它是单步的瞬时值，`/context` 与 trace 里都留着。

### 点占比数字看柱状图

点数字在状态栏上方展开柱状图，左边是条，右边是类别与 token 数：

```
████████████████████████  近期对话    18.9K
████████░░░░░░░░░░░░░░░░  工具定义     6.4K
██████░░░░░░░░░░░░░░░░░░  阶段事件     4.6K
```

七层来自 `ContextAssembler` 的 `usage`，工具定义来自同一份度量里的 `tools`，
「其他开销」是服务端记账与装配估算之差。只列非零项，按 token 数从大到小排；
条长按最大项缩放，类别与数字靠右排。

面板宽 48 格，底边紧挨状态栏；水平中心按点击时数字所在列计算，再夹在屏幕内。
数字中心距屏幕右沿 24 格，面板半宽也是 24 格，所以在 80、100、120 列下中心都能
正好对上。每步的装配度量经 `context.metrics` 事件送到界面，柱状图读的是循环层
现场记下的那一份，与 `/context`、trace 同源。

### 提示条改成浮层

`ToastRack` 原来 `dock: bottom`，占的是屏幕底部的真实行：一条短提示让出两行
（消息区失焦时 28 → 26、聚焦时 26 → 24），折成两行的长提示让出三行；显示期间整块界面
上移，消失后复原，看起来像界面抖了一下。

改成 `overlay: screen` + `position: absolute` + `constrain: inside inside`，容器脱离布局流，
一行都不占。Textual 的绝对定位只能给一个偏移量，没有「贴右下角」这种写法，所以偏移量取
`999 999`，再由 constrain 拉回屏幕内——落点只由容器自身尺寸决定，与终端高矮无关。
外边距留出右边 2 列、底部 1 行（状态栏的高度），提示条出现在状态栏上方。

容器宽度跟着最宽的那条提示走，不铺满整行。铺满时容器看不见，却实实在在盖住屏幕最底
那几行：点击落在它身上就到不了底下的组件，而消息区底部的「有新内容」提示正好停在那几行，
提示条挂着的那三秒里点它没有任何反应。宽度写 auto 量出来的是提示条正文折行之前的宽度
（46 个字的提示量出 95 列：46 个全角字符 92 列、字形 1 列、左右内边距 2 列），
长提示被 `max-width: 60vw` 收窄之后容器还留在原尺寸，提示条反而浮在离右边缘二十几列的地方。
所以宽度由 `ToastRack.fit()` 按提示条排版之后的实际尺寸回填，`ToastNotification.on_resize`
负责在尺寸定下来时叫它。同一条 46 字提示实测：80 列终端上容器 48 列（撞 60vw）、
120 列上 72 列（撞 60vw）、200 列上 95 列（上限不起作用，按正文自然宽度）。

100x30 实测：

| 场景 | 消息区 | 状态栏 | 提示条 |
| --- | --- | --- | --- |
| 没有提示 | 0..25，26 行 | y=29 | 无 |
| 一条短提示 | 0..25，26 行 | y=29 | (89,28) 9×1 |
| 长短各一条 | 0..25，26 行 | y=29 | (38,26) 9×1 与 (38,27) 60×2 |

改动之前同样这两条会让消息区退到 24 行与 22 行，状态栏跟着上移到 27 与 25。

120x40 上同时挂三条短提示时，容器落在 x=96..118、y=36..38。消息区底部的「有新内容」
提示在 y=37 横跨 1..116，点它的中间一格仍然能回到底部；只有落在提示条盖住的那几列才会
被挡住。

### 判据

`tests/test_smoke.py` 补了两条：状态栏右端文案以「上下文 」开头、含 `/`、以 `%` 收尾；
提示条容器的宽度等于最宽那条提示的宽度，且小于屏幕宽度。

`tests/test_smoke.py` 4242 项、`tools/check_prefix.py`（前缀 1852 token）、
`tools/check_web_api.py` 59 条、`tests/dump_layout.py` 四份快照全部通过。

## 八、左栏与会话树（2026-11-05）

聊天界面从两栏变成三栏：左栏 `#chat-rail`（30 列）、中间消息区、右栏 `SidePanel`。

左栏上半是会话树：根会话按更新时间排，子 agent 缩进挂在父会话下面，当前会话用一行底色

30 列左右的导航在 80 列终端里会把正文挤成一行几个字。

`SidePanel` 多了一段「产物」：从 `Event.artifacts` 里取 handle，按主题倒序最多列六个。
只看名字：handle 只在产出它的会话里有效，路径要去运行目录看。

## 十、同宽、可调宽与左栏（2026-11-06）

**输入框与消息区同宽。** 原先 `EditorPane` 是聊天界面的最后一个子组件，横贯整屏；
消息区夹在左右两栏之间，于是输入框比对话多出两侧的宽度。现在中间那一栏 `#chat-main`
同时装 `MessagesPane` 与 `EditorPane`，两块宽度由同一个 `1fr` 决定，输入框的左右边界
与对话相同：120x40 实测两块都是 x=31、宽 69。输入框的 `padding: 0 3` 与消息正文的
三层内边距相加都是 5 列，文字也从同一列起。

**三条界线都能调宽。** 新增 `widgets/splitter.py`：1 列宽、可聚焦，鼠标按住拖动或按
左右键各调一格，悬停转一档灰、按住转强调色。`HomeScreen` 的左栏与 `ChatScreen` 的左右栏
各配一条；右栏那条的方向取 `sign=-1`，界线往左推是右栏变宽。界线只发
`ResizeRequested` / `ResizeFinished`，宽度由界面改 `styles.width`，两者各记一份的话
拖几次就会对不上。

宽度存在状态文件（`rail_width` / `side_width` / `home_rail_width`），松手或按键调完写一次；
拖动过程中每移一格都写一次 `state.toml` 太重。画的时候按当前终端再夹一次：
左栏 16–60、右栏 20–60、主界面左栏 20–60，并在放得下时给中间那一栏留 40 列
（终端窄到两栏的最小值加起来都放不下时，先保两栏的最小宽度）。
夹的是画面上的宽度，状态文件里那份不动——终端临时缩窄不该把设定改掉，宽回来之后
原来的宽度还原。右栏收起时它的界线跟着收起。

**左栏重排。** 会话树与主题清单之间加一条 `border-top`，两段各自滚动。分节标题带条数
（`运行中 2` / `全部任务 5` / `主题 3 · 12 步`）：栏拖窄之后标题只剩几个字，数字是唯一
还读得出来的信息。主题行的标题补齐到栏宽，状态字形一律停在最右列，竖着扫一列就知道
哪一条还在跑；进行中的主题序号用强调色。

两个列表都记住了上一次画出来的内容：会话的键、标题、状态、当前项与栏宽都没变时
不重建，主题的条数与宽度没变时只改文字不重建行。每一步都会刷新左栏，重建一次等于把
滚动位置推回顶部，用户正翻着更早的会话或主题就会被弹回去。主题多出来时才跟着滚到底，
用户翻着旧条目时不打断他。

判据在 `run_splitter_checks()`：方向键与拖动各改一次宽度、夹到下限、两条界线互不影响
（消息区始终与输入框同宽）、松手后写进状态文件、重新读回状态文件、终端缩到 90 列再放大回来。
左栏那几条在 `run_rail_checks()`：分节标题带条数、主题行补齐到栏宽、内容没变时不重建。

## 十二、最近任务的字段（2026-11-06）

一行里依次是标题、状态、「N 主题 · M 产物 · 时间」与最近一次结果。结果取最后一条封存
主题的 `summary`；没有就取它的 `issues[0]`；再没有就取 `status_note`（正在跑的任务
只有这一项）。产物数是各主题 `artifacts` 去重之后的条数。

结果按剩余宽度截断：`SessionRow` 的两列内边距、状态词 6 格与它前后各两格的空隙、
meta 前面的分隔一共占 13 格，标题留 12 格，所以结果最多 `width - 27 - counts` 格，
不够 6 格就不写。100x30 实测内容宽 63、计数段 23 格，结果拿到 13 格，标题 12 格。

`SessionRow.render` 的预留从 6 格改成 10 格：原来只算了「运行中」6 格，它前后
各两格的空隙漏在外面，状态词为「运行中」时整行比内容区宽出 3 格，末字被裁掉。
可用宽度同时减去左右各一列内边距。

判据在 `run_home_recent_checks()`：四条任务分别走「有结论」「有失败原因」「什么都没跑」
「只有状态说明」四条来源；每行不超出内容宽度、标题保留开头；窄到 57 格时结果截断，
50 格时只写计数。

## 十三、主界面快捷入口（2026-11-06）

输入框下面一行三个模板：`研究` / `结构` / `知识`，前面一个「快速开始」标签。点一下把

它们只是文字，不引入新的执行路径。

这一行加上上方间距占 2 行。24 行终端里除输入区以外已经占掉 20 行，所以
`apply_quick_visibility()` 在终端高度不足 26 行时整行收起。100x30 实测这一行在 y=19，
最近任务从 y=21 起。

判据在 `run_home_quick_checks()`：三个模板的字与顺序、位置在输入框与最近任务之间、
点击后文本整段替换且光标停在末尾、不跳界面、24 行收起、回到 40 行又出现。

## 十八、主题的结局先于封存（2026-11-06）

未封存那一段的状态由 `topics._stopped_status` 判定，顺序是：

1. `session.status == "cancelled"` → 已中断；
2. `session.status == "failed"` → 失败；
3. 最后一步有未决项 → 失败；
4. 有步 → 未封存；
5. 没有步 → 已完成。

前三条都不必等轮末封存。原先只有「有步 / 没步」两档，用户按停之后标题仍写「进行中」，
事后也分不出这一段是被停下的还是进程断掉的。

说明行跟着改一处：进行中的主题如果前面某一步失败过，第二行变成
`失败：<原因> · 正在运行 <工具>`，颜色从运行中的蓝换成 `#C62828`。失败排在前面，
读者先看到异常，再看当前在做什么。

中断时界面自己调 `messages.set_running(False)`：取消这条路不走 `turn.done`
（`loop.py` 明说跳过收尾），不收回来的话主题头会一直写着「进行中」。

判据在 `run_topic_state_checks()`：四种状态各一条，加一条「进行中失败过的说明行以
失败开头」。

## 十九、工具过程的三级展开（2026-11-06）

三层各有各的开关，互不覆盖：

- **主题**：点标题行收起或展开整段，用户消息不跟着收。
- **步**：点步行收起或展开这一步的工具卡，行本身留在原处当入口。
- **输出**：主题头最后一行 `▸ 展开全部工具` / `▾ 收起全部工具`，一次作用于本主题
  全部工具卡；再下一级是单张卡片的标题行。

主题级开关只在主题展开且有步时出现：收起状态下工具卡本来就不在画面上。它只管输出
这一层，步行的展开状态不动。

`/details` 从「全局展开所有卡片」改成就地展开最后一个主题（与那个按钮同一个函数）。
`SessionManager.show_details` 整项删掉，状态文件里不再有这一项：一次全开会把挂载窗口
里几十张卡一起摊开，滚动长度与每帧重排的代价一起涨，下次打开会话还是展开的。

收起的主题在说明行里写工具名：最多三个、总宽 24 格，余下的写 `+N`，后面接结论。
标题行的计数从「N 个工具」改成「M 次调用」——同一个工具调两次是两次调用，名字只列一次。

工具卡展开后依次是参数、输出、产物：

- 参数：全部键值一行一个，值超过 160 字符截断。标题行只装得下第一个键。
- 输出：保持开头三行 + 省略行 + 末尾三行的分法。
- 产物：`tool_meta` 的 `handle` / `ref` / `run_id`，与步的流水共用
  `event_log.artifact_refs()`。
- 失败那一刻卡片自己展开：标题行变红只说明出了事，错误原文才可用。

**折叠之后的滚动位置按锚点算。** 补偿量取锚点那一块组件的屏幕行差：被点的主题头、
被点的步行，或者视口最上面那一块。改完把它放回原来的行，用户正在看的那一段就不动。
按总高度差补偿只在变化的行全部位于视口上方时成立，点击折叠发生在视口里面，照那个
式子算会让整屏平移同样的行数。补偿之后不再贴底就把跟随关掉，下一次流式输出不会把
视口拽回底部；锚点缺失时退回高度差，自动折叠走的就是这一条。

判据在 `run_tool_card_checks()`、`run_topic_card_checks()` 与 `run_topic_scroll_checks()`：
参数段默认不占位置、展开后三个键都在、产物行从 `tool_meta` 取、失败自动展开、
主题开关只动本主题、三层折叠之后头部与步行的行号不动。
