# 真实会话里看到的失败模式

2026-10-25 两次真实会话（deepseek-flash / 1M 窗口），同一组三问：

1. 「查一下人 EGFR（P00533）在 PDB 里有哪些结构，挑一个带小分子抑制剂的给我编号」
2. 「把 4HJO 的结构取下来并登记成受体」
3. 「把 4HJO 写成一个运行目录，告诉我里面有哪些文件」

两次都跑完了，也都做成了；但同一组问题输入 **442K 与 135K**，差 3.3 倍。
差的那 3 倍几乎全在第 1 轮的步数上（24 步对 7 步）。这份文件只记账，不改代码：
每条写清现象、证据、根因在哪、代价多少，以及**是不是当初刻意的**——刻意的那些
要改就得连理由一起改。

| # | 现象 | 代价 | 根因位置 | 刻意？ |
| --- | --- | --- | --- | --- |
| F1 | `load_tools` 把被关掉的工具报成「已装入」，模型调它拿到「请改用别的办法」，于是 bash 自建 RCSB 客户端 | ~20 步 / 300K 输入 | `toolset.py:95`（列的是 `catalog()` 而非注册表）+ `loop.py:130`（禁用文案） | 否 |
| F2 | 模型在 Linux 上写 Windows 命令 | 2 步 | `prompt.py` 的 `SHELL_DISCIPLINE` 写死「这套环境是 Windows」 | 否 |
| F3 | 猜错 handle 编号，`open_viewer` 失败 | 1 步 | 上下文里没有「当前有哪些 handle」的索引 | 否 |
| F4 | 模型不知道状态目录在哪，先试 `./.opencode_tui` | 2 步 | 上下文里没有工作目录 / 状态目录 | 否 |

## F1 · 装族说「装好了」，那个工具其实是被关掉的

**现象**：第 1 次会话第 1 轮，模型 `load_tools({"family": "rsearch"})`，工具回
「已装入 rsearch：search_pdb。下一步起这些工具出现在清单里」；下一步它调
`search_pdb({"query": "P00533"})`，收到的是「已被禁用……重试无用，请改用别的办法」。
它没有再试别的领域工具，而是 `bash` + `urllib` 自己写脚本拉 RCSB，连写三个
`.probe/*.py`，第 1 轮因此用满 `MAX_STEPS=24`。

**证据**：`.opencode_tui/tools.toml:12` 写着 `search_pdb = false`（同一份还关了
`search_literature`、`switch_receptor`）。装配时它们**不进注册表**
（`app._build_registry`），但 `LoadToolsTool` 列的是 `catalog()` 里的名字——
那是「有哪些工具」，不是「装进来了哪些」。于是它把一件永远装不进来的工具报成
「已装入」，模型照着这句话去调，撞上禁用清单。

两句原文可以复现：

```
load_tools 说： 已装入 rsearch：search_pdb。下一步起这些工具出现在清单里，参数按各工具的说明给。
模型看到的话： search_pdb 已被禁用（配置在 .opencode_tui/tools.toml 里，可在 /tools 面板里打开），
              本次会话不会提供这个工具，重试无用，请改用别的办法或告诉用户。
```

**为什么第一次归因错了**：我事后手动跑 `SearchPdbTool().execute({"query": "P00533"})`
拿到 391 条命中，就判成「那次是瞬时失败」。直调工具绕过了注册表，也就绕过了
禁用清单——它证明的是「工具本身好用」，不是「当时它被装进来了」。真正的判据是
注册表里有没有它：`registry.get("search_pdb") is None`。

**代价**：约 20 步、300K 输入。同一组问题两次跑，442K 对 135K，差的就是这一段。

**已修**（2026-10-25）：

1. **`load_tools` 减去禁用清单**。新增 `registry_argument` 注入通道（与
   `context_argument` / `task_argument` 同一套声明式注入），`LoadToolsTool` 拿注册表
   只读一件事：`registry.disabled`。整族被关时直接失败并说清「都被项目配置关掉了」；
   只关一部分时列可用的那些，并注明谁被关掉了。**顺带改了划分**：`search_pdb`
   从 `rsearch` 族并进 `structure`——原先那一族只有它一个，说明却写着「反向检索」。
2. **禁用文案不再教绕道**。原句「请改用别的办法或告诉用户」改成「不要用 bash 自己
   实现它，也不要换数据源绕过——把这件事告诉用户，由用户决定是否打开它」。
   `search_literature`、`switch_receptor` 同样被关着，这条对它们一起生效。

判据在 `tool-family` 组：整族被关时 `load_tools` 必须失败、不许出现「已装入」、
文案里必须同时有「关掉」与「bash」；禁用文案里不许出现「别的办法」。

## F2 · Linux 上写 Windows 命令

**现象**：第 2 次会话第 3 轮，模型执行 `bash("cd runs/4hjo && dir /s /b ...")`，
失败，改用 `ls -la` 才拿到文件清单。

**代价**：2 步。不致命，但它是「模型不知道自己在什么平台上」的直接证据。

**根因（2026-10-26 更正）**：不是「缺一条环境信息」，是**系统提示在说谎**。
`prompt.py` 的 `SHELL_DISCIPLINE` 里那句「这套环境是 Windows，命令按它的语法写：
用 dir 而不是 ls」是写死的——它在 Linux 上跑的时候**就是在教模型写错命令**。
模型不是猜的，是照着提示做的。判据那边也一样：`test_agent.py` 里有一条
「提示里点明这是 Windows」，把这句话锁住了，所以它一直没被人发现。

**已修**（2026-10-26）：那句话改成按 `sys.platform` 现取（`prompt.platform_note()`）。

- 平台是**本机常量**，所以放在 `PREFIX` 里而不是易变头里：同一次运行每个字节都一样，
  不伤缓存，而且它在 `system` 角色下比一条 user 消息更管用。这偏离了计划表里
  「平台放进 HEADER」的写法，理由记在计划文档那一行。
- Linux / macOS 那句反过来点名「Windows 的 dir、copy、findstr、type 在这里不存在」；
  Windows 分支保留原来那句（它本来是从现场攒出来的，只是不该在别的平台上出现）。
- 判据：`--only env-block`，含「linux 上不许教 dir」与「平台那句与 `sys.platform` 一致」；
  原来那条锁死 Windows 的断言改成按实际平台判。

**复测**（同日，干净家目录，两问：取 4HJO 登记成受体 → 状态目录在哪、列出来、今天几号）：
五条 bash 全是 POSIX 写法（`date`、`cat`、`ls`、`for d in ...`），
**没有一条 `dir` / `findstr` / `netstat -ano`**。同一台机器上改之前是
`dir .opencode_tui\structures 2>nul`，还顺手在仓库根建了个 `nul` 文件。

**建议**：~~与 Phase 4 的 ENV 块合并解决~~——已按上面的方式修掉。`bash` 失败回执
里补「当前平台是 linux」这条退路不用做了：根因在提示，不在回执。

## F3 · 猜错 handle 编号

**现象**：第 1 次会话末尾 `open_viewer({"run": "artifact#2"})` 失败——当时登记表里
只有 `artifact#1`。模型是照前几步见过的编号推的，隔了几步就记串了。

**根因**：handle 只在**工具返回的那一刻**出现在上下文里，之后要么进了证据层、
要么随旧工具结果被清掉。模型要用的时候手里没有索引，只能凭记忆。

**建议**：Phase 4 的「产物索引」正好治这个——`SessionLedger.digest()` 给当前受体
+ 最近 5 个产物，≤10 行。这条不是锦上添花，是**上面这次失败的复现条件**。

**已修**（2026-10-26）：`SessionLedger.digest()` 每次发问现算一份索引，
`loop._digest_text()` 取它，`ContextAssembler` 把它排在 TASK 层里（任务状态之后、
摘要之前），所以它进的是那条**易变的 user 头**，`system` 前缀一个字节不动。

- 索引内容：一行提示（「照抄，不要按前几步的编号往后推」）+ 当前受体 +
  最近 5 个产物（`共 N 个，只列最近 5 个`）+ 配体集的 handle。上限 10 行、
  每行 60 字，摘要压成一行并截断。
- **不调 `reconcile()`**：那一步会把登记过的每个路径读一遍算指纹，而这段每步
  都要算；`file_state` 用上一次对账的结果——不新鲜也不会把编号指错。
- 已搁置的条目（切换掉的旧受体下面那些）不列：列出来等于让模型去用一个
  「已经不在当前工作区」的 handle。
- 用量记在 `Layer.TASK` 上：单开一层要动 `Layer`、降级链与 `/context` 的显示，
  而它只有百来个 token。
- 判据：`tests/test_agent.py --only ledger`（空表、行数与长度上限、只列最近
  5 个、搁置的不列、`system` 逐字节不变、TASK 用量变大、没装配登记表时是空串）。

**复测**（同日，干净家目录，三问：取 4HJO → 写运行目录 → 在查看器里打开）：
`open_viewer({"run": "artifact#1"})` **一次就对上**，回执里没有「登记表里没有」，
只有「本地结构服务没有在监听」——那是无头跑的时候没人起网页服务，不是编号问题。
4 步做完前两问，总命中率 94.9%，索引没有把缓存打掉。

同一轮里还看到两件事，都不是这条的：

- 索引一开始把**旧会话**的条目也列了出来（那次实验复用了 `ses_0001`，
  登记表快照是按会话编号存的）。这提醒一句：索引说的是「这张登记表现在有什么」，
  会话编号撞车时会话之间就会互相看见。
- 服务没起来时模型不信那句话，自己去 `netstat | findstr`（又是 Windows 命令）
  并 `nohup serve_web.py` 起了服务——10 步。这是 F2 的加强版，属于「回执里
  给出的下一步动作太含糊」这一类，记在这里，暂不改。

## F4 · 不知道状态目录在哪

**现象**：第 1 次会话第 1 轮，模型执行
`bash("cd .opencode_tui/targets && python -c ...")`，失败（相对路径没有这个目录），
随后 `ls ~/.opencode_tui` 才找到。

**根因**：这次实验的状态目录在 `/tmp/vsa-lazy-session`，模型默认它在
`./.opencode_tui`。它没有「状态目录 / 工作目录是哪个」的任何信息，只能猜。

**建议**：并入 ENV 块（工作目录 + 状态目录 + 平台 + 日期）。注意必须放在
**易变区**：日期进了 `PREFIX` 就每天击穿一次缓存，还会红掉
「PREFIX 连续两步字节相等」那条判据。

**已修**（2026-10-26）：`prompt.environment_block()` 排在 user 头最前（`loop._env_text()`，
状态目录由 `app.py` 把 `state_path.parent` 交给循环层）：

```
（运行环境：今天 2026-10-26）
- 工作目录：/data/work/zq/project/VSAgent（runs/、corpus/、logs/ 都在它下面）
- 状态目录：/tmp/vsa-env-session（state.toml、connection.toml 在这里，不在工作目录下）
```

- **只写日期不写时分**：带上时间的话这一头每一步都和上一步不同，缓存从这一条起
  全部作废——那正是把 `Workspace.state_text` 从系统提示里搬走的理由。
- **不写「ledgers/ 也在这里」**：登记表快照固定落在 `~/.opencode_tui/ledgers`，
  与 `state_path` 无关；`state_path` 被改到别处时（测试与脚本常这么干）那句话就是假的。
  复测里模型正是照着我写错的那半句去 `$HOME/.opencode_tui` 找登记表的。
- 判据：`--only env-block`（日期只到天、两个目录都在、不进前缀、`system` 逐字节不变、
  TASK 用量变大、应用确实把状态目录交给了循环层）。

**复测**（与 F2 同一次会话）：环境块写着 `/tmp/vsa-env-session`，模型**第一条**
bash 就去那里读 `connection.toml`，没有再 `cd .opencode_tui`。它随后还翻了
`$HOME/.opencode_tui`——那是在找「登记表」放哪儿，属于上面那半句写错导致的，
不是没看见状态目录。

## 已修 · 重试语义一直没接线

`RetryableToolError` 的 docstring 写着「与 `ToolError` 分开，是为了让重试逻辑只重试
这一类」，但 `loop.py` 的 `_execute_tool` 用 `except ToolError` 把它一起接住了——
**工具层一次都不重试**，那个标签等于白写。四处 `except Exception`
（`rsearch.py:253` / `:320`、`complexes.py:241` / `:332`）连标签都吃掉。
这两次会话里没有证据触发过它，但它与 F1 是同一个病：**说好要重试的东西没人重试**。

2026-10-25 接上：

- 循环层加 `except RetryableToolError`，重试 `MAX_TOOL_RETRIES = 1` 次，间隔用已有的
  `RETRY_DELAYS[0]`，界面发 `PartType.RETRY`（与模型请求重试同一个类型）。
- **只重试 `execute`**，不重跑权限与钩子：那两步是本地判定，用户已经点过允许，
  重跑只会把同一个问题问第二遍。
- 四处 `except Exception` 前补 `except RetryableToolError: raise`。
- 重试用尽的文案写明「不是参数错、不要用 bash 自己实现、不要换数据源绕过」——
  最后半句正是第 1 次会话缺的那句。
- 判据：`tests/test_agent.py --only tool-retry`，13 条，含「普通 `ToolError` 不重试」
  与「可重试错误能穿出 domain 层」。

为什么工具层只重试 1 次而不是 2 次（模型请求那层是 2）：一次工具调用的超时本身就有
几十秒，重试两次等于把一次网络抖动拖成三倍等待；工具失败之后模型还有别的路可走，
一次就够把「抖了一下」与「真的不通」分开。

## 不需要改的（正面证据）

- **按需加载不用教**：两次都自己 `load_tools`，按 structure → uniprot → rsearch →
  export（→ listing）装 4–5 族，没有一次需要提示。每步工具定义 3.1K → 6.0K，
  全量是 12.3K。装族那一步命中率 98.9% → 36.6%，下一步回到 95.9%——一次性。
- **说清下一步的失败文案是有效的**：第 2 次会话模型叫了 `search_pdb({})` 空参数，
  收到的是禁用文案（不是「至少要给一个条件」——那也是我事后直调才看到的），
  它没再纠缠，直接用已知编号取结构。同一个工具，第 1 次绕了 20 步、第 2 次一步没绕，
  差别在模型当时手上有没有别的路。
- **零命中不再被当成失败**（`EmptyResult` 那次修正）在这两次里没再触发误判。
